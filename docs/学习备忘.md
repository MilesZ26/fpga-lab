## 1. `$readmemh` 的相对路径一定失败

> **2026-10-18 宏名更新**：下面这段历史里写的是 `LUTDIR`。现在**一个表一个宏**：
> NCO 的表用 `NCO_LUTDIR`，FIR 系数用 `FIR_COEFDIR`（`nco.v` 仍兼容旧名 `LUTDIR`）。
> 原理完全一样，只是宏名不能再全仓库共用一个。

### 现象

- **iverilog**：表里全是 `x`，波形一片红，**不报错、不警告**。
- **Vivado 综合**：日志里两条 `CRITICAL WARNING`，然后**整个模块被优化掉**：

```
CRITICAL WARNING: [Synth 8-4445] could not open $readmem data file
  's01_nco/lut/sin.mem'; please make sure the file is added to project and
  has read permission, ignoring  [nco.v:23]
```

- **板上症状**：四颗 LED **全灭**（表全 x → 综合成常量 0 → `fsin_o = 0`）。

### 原理

**`$readmemh` 的路径是相对"仿真/综合进程的工作目录"，不是相对 `.v` 文件所在目录。**

- iverilog：`sim.sh` 里 `vvp` 在 `build/` 里跑 → 相对路径必然找不到。
- Vivado：run 目录是 `<工程>.runs/synth_1/`，由 `runme.bat` 里的
  `cd /d "%HD_SDIR%"`（`HD_SDIR` = runme.bat 所在目录）设定。仓库在别的盘/别的目录，
  所以 `"s01_nco/lut/"` 这种相对路径**永远对不上**。

### 怎么查

1. **看到"输出恒为 0 / 全灭"，先怀疑表**，而不是逻辑。
2. `report_utilization` 看 **`Block RAM Tile`**：表真进去了应该 > 0；是 0 就是没读到
   （详见第 3 节）。
3. Vivado 日志里搜 `8-4445` 或 `readmemh`。

### 结论（s01 实测）

| 做法 | 结果 |
|---|---|
| RTL 里写相对路径 `"s01_nco/lut/"` | ❌ 仿真、综合都读不到 |
| **把 `.mem` 加进工程 source** | ❌ **没用**（实测过。Vivado 报错里那句 "please make sure the file is added to project" 是**误导**——加进去它也不会去搜） |
| **`-verilog_define NCO_LUTDIR="<绝对路径>/"`** | ✅ **正确解法**（当年叫 `LUTDIR`） |
| 把 `.mem` 拷到 run 目录下的 `s01_nco/lut/` | ⚠️ 能work但只是诊断手段，会造成"仿真/综合各用一份独立数据"，**别长期用** |

工程模式下的填法：**Settings → Synthesis → Options → More Options**：

```
-verilog_define NCO_LUTDIR="D:/Backup/Documents/GitHub/fpga-lab/s01_nco/lut/"
```

⚠️ **值里必须带真正的双引号**，**结尾的 `/` 不能少**（RTL 里是
``$readmemh({`NCO_LUTDIR, "sin.mem"}, rom)`` 拼起来的）。少引号会变成非法 Verilog。

## 2. 改了参数却没生效：顶层覆盖 + 一个字母

这是 s01 上板时**最贵的一个坑**，连续两轮综合+实现都白跑。

### 坑 A：改了底层模块的默认参数，但被顶层显式覆盖

```verilog
// nco.v
parameter integer FREQ_HZ = 100_000,   // ← 在这里改成 100 kHz

// nco_top.v
nco #(
    .FREQ_HZ(FREQ_HZ),   // ← 传的是 nco_top 自己的 FREQ_HZ = 1
) u_nco (...);
```

**只要顶层实例化时显式传了这个参数，底层模块的默认值就完全不起作用。**
改了等于没改，而且**没有任何报错**。

> **规律：模块的 `parameter` 默认值只在"没人覆盖它"的时候才生效。**
> 想改行为，要改**实际被传进去的那个值**——也就是顶层的参数，或者顶层实例化时写死的值。

**怎么查**：别猜，去看综合真正执行的命令行。Vivado 会把它写成
`<run>.runs/synth_1/<top>.tcl`：

```tcl
synth_design -top nco_top -part xc7a100tfgg484-2 -verilog_define NCO_LUTDIR="..."
```

宏定义、top、器件、任何 synthesis option 都在这行里，一目了然。

### 坑 B：宏名少一个字母

```tcl
-verilog_define LUDIR="D:/.../s01_nco/lut/"    ← 少了一个 T
```

RTL 里判断的是 `` `ifndef NCO_LUTDIR ``，于是判定"没定义"，走了兜底相对路径 →
回到第 1 节的坑。

**症状的特征**：报错信息里显示的路径是 **RTL 里的兜底路径**（`s01_nco/lut/sin.mem`），
而不是你填的绝对路径。**看到这个就说明你的宏压根没生效**，不用往下查了。

## 3. 怎么判断"表到底进没进设计"

**`report_utilization` 比日志更硬** —— 日志里的 warning 可能被淹没，资源报告骗不了人。

s01 实际数据对照：

| 指标 | 表**没**读进去 | 表读进去了 |
|---|---|---|
| `Block RAM Tile` | **0** | **3**（RAMB36×2 + RAMB18×2） |
| `Slice Registers` | **2** ← 只剩 `reset_sync` 的两个触发器 | **35** |
| `Slice LUTs` | 25 | 18 |
| 综合日志 | 2 条 `Synth 8-4445` | 0 条 |

**为什么表死了会连寄存器都没了**：表内容全 `x` → `fsin_o` 恒 `x`/0 →
下游（LED）是无所谓的 → 相位累加器、输出寄存器、ROM 全部变成 don't-care，
被综合**整块删掉**。所以"寄存器数少得离谱"本身就是"上游没数据"的信号。

> **一般化的教训**：资源用量比预期**少很多**，往往不是"优化得好"，
> 而是**有东西被优化没了**。先去查它该不该在。

顺便：日志里 `INFO: [Synth 8-7052] ... no optional output register could be merged`
说明 ROM 是满宽推断出来的（`fsin_o_reg | 4096x12 | Block RAM`），这行是有用的正面证据。

## 4. 有符号 vs 无符号：ILA 上 "∩ + ∪" 的经典症状

### 现象

ILA 抓出来的波形**不是正弦**，而是**一段开口向下、一段开口向上**（像个倒扣的碗挨着一个正放的碗）。

### 原理

NCO 的 ROM 是**12 位二进制补码**，取值 `-2047 … +2047`。
但 `nco.v` 的端口声明**没写 `signed`**：

```verilog
output reg [11:0] fsin_o,    // ← 位模式是补码，但类型是无符号
```

**位模式完全正确，丢的只是类型信息。** 而 ILA 按信号声明的类型选默认显示方式，
于是把负数映射成 `v + 4096`：

| 相位 | 真值（有符号） | 无符号显示 |
|---|---|---|
| 地址 0 | 0 | 0 |
| 地址 1024 | **+2047** | **2047** |
| 地址 2048 | 0 | 0 |
| 地址 3072 | **−2047** | **2049** |

画出来：
- 前半周期 `0 → 2047 → 0` = **∩（开口向下）**
- 后半周期 `0 →(跳) 4095 → 降到 2049 → 回到 4095 →(跳) 0` = **∪（开口向上）**

### 怎么解

1. **看波形**：ILA 里右键信号名 → **Radix → Signed Decimal**。
   （这本身就是验证：改完变正弦，就说明是显示问题而不是逻辑问题。）
2. **改代码**（s01 已做）：端口声明加 `signed`：

```verilog
output reg signed [AW-1:0] fsin_o
```

### 为什么这件事很重要（不是显示问题）

**`s02_mixer` 要做复数乘法。** 拿无符号端口去乘，正半周对、负半周全错——
**而且错得很隐蔽**。所以 `s01_nco/TASK.md` 最后那句"接口先想好"说的就是这个。

> **规律：模块边界的"有符号性"是一种接口约定，必须在接口上就表达清楚。**
> 内部 `reg signed` 一旦赋给无 `signed` 的端口，类型信息就在边界上丢了。

## 5. `mark_debug` 不够，要 `keep`

```verilog
(* mark_debug = "true" *)               wire [11:0] fcos_o;   // ← 不够
(* mark_debug = "true", keep = "true" *) wire [11:0] fcos_o;   // ← 这样才对
```

- **`mark_debug`**：只是给 Vivado 的 "Set up Debug" 向导看的**标记**，
  **不保证**阻止综合把这个网优化掉。
- **`keep`**：明确禁止综合优化掉这个网。

**s01 的实测后果**：`fcos_o` 没接到任何引脚（只给 ILA 用），
只写了 `mark_debug` 时，综合把 `fcos_o` 和 `fsin_o[7:0]` 这些"没接到引脚的位"裁掉了 ——
Set up Debug 的候选列表里**根本找不到这些网**。

> **规律：只要一个信号"不驱动任何输出引脚"，就要主动声明你想留住它。**
> 综合器没有理由替你保留。

## 6. ILA 使用要点（触发、窗口、开销）

### 6.1 先说最重要的：采样窗要装得下至少一个周期

ILA 用 `clk`（50 MHz）采样，缓冲深度只有几千点。
**8192 点 = 8192 × 20 ns = 163.84 µs。**

| `FREQ_HZ` | 周期 | 窗口内能看到 | 结果 |
|---|---|---|---|
| 1 | 1 s | 0.016% 个周期 | **一条直线** |
| **100 k** | 10 µs | **16.4 个周期**（每周期 500 点） | ✅ 光滑正弦 |

**所以看波形和看 LED 心跳是两次不同的 bitstream。**

### 6.2 ILA 核**不能写进 RTL**

它是 Vivado IP，iverilog 没有它的行为模型 —— 写进 `.v` 会让 `make sim` 直接编译不过。
正确做法：综合后用 **Set up Debug** 挂上去（它会写进 XDC）。

### 6.3 捕获窗是**以触发点为中心**的

ILA 是循环缓冲：触发命中后**再录半个窗口**才停。默认触发点落在窗口 **50%**。

所以"我触发在峰值，为什么波形不从峰值开始"——**峰值就在窗口正中**，
前半窗是触发**之前**录的数据。这是正常行为。

想改要动 ILA 核的 "Trigger position in window"，**得重新实现**——不值得为显示问题重跑。

### 6.4 为什么触发操作符里没有 rising edge

**边沿操作符只对 1 位信号出现。** ILA 的 probe 是**总线**（`fsin_o[11:0]`），
而 Trigger Setup **只能选整个 probe，不能切片**，所以只有比较类操作符。

真要边沿：加一个 1 位 probe，或者开 **Advanced Trigger**（`C_ADV_TRIGGER true`，
有 `$rise()` / `$fall()`）——**都要重跑实现**。

### 6.5 别用 `== 峰值` 当触发条件

**地址每拍跳 ~8.19**（`PHI_INC / 2^LUT_AW`）。表里 4096 个地址，一个周期只采到约 500 个，
**其余 ~3600 个根本不会被访问**。峰值 `+2047` 在表里**只有一个地址**（1024），
能不能踩上是碰运气。

**更稳的写法：用阈值。** 因为**正弦顶部很平**：

| 触发条件 | 覆盖地址范围 | 每周期命中 |
|---|---|---|
| `fsin_o == 7FF` | 只有 1024 | 平均 **1/8** 概率 |
| `fsin_o >= 7F0` | ≈ 945 ~ 1103 | 约 **19** 个采样点 |

### 6.6 为什么 `opt_design` 特别慢

加了 ILA 之后，`opt_design` 阶段要**现场生成并综合 `ila` + `dbg_hub` 两个 IP 核**：

```
Phase 1 Generate And Synthesize Debug Cores
  Generating Script for core instance : dbg_hub
  Generating Script for core instance : u_ila_0
```

s01 实测：`opt_design` **3 分 04 秒**，而 `place` 9 秒、`route` 39 秒。
**不是设计慢，是调试核的固定开销**，每次跑实现付一次。

顺带：`keep`/`mark_debug` 会让综合器"想优化但被拦住"，日志里能看到
`In phase Sweep, 889 netlist objects are constrained preventing optimization`。

### 6.7 调试开销有多大（s01 实测）

| 指标 | 无 ILA | 有 ILA | 开销 |
|---|---|---|---|
| Slice LUTs | 18 | **1117** | +1099 |
| Slice Registers | 35 | **1971** | +1936 |
| Block RAM Tile | 3 | **9** | +6 |
| BUFGCTRL | 1 | 2 | +1 |

**调试开销是设计本身的 60 倍** —— 正常，不用慌。

### 6.8 采样深度是 **2 的幂**：是 8192，不是 8196

Set up Debug / `C_DATA_DEPTH` 里能填的深度只有 **2 的幂**：
`1024 / 2048 / 4096 / 8192 / 16384 / 32768 …`。写 `8196` 这种数不是"多 4 个点"，
而是根本不是一个合法选项。

本仓库一直用 **8192**（s01/s02 都是，见 `s02_mixer/constr/mixer.xdc` 里
`set_property C_DATA_DEPTH 8192`）。为什么是 8192：

| 量 | 值 | 怎么来的 |
|---|---|---|
| 采样点数 | 8192 | 深度 |
| 窗口时长（50 MHz） | **163.84 µs** | 8192 / 50 MHz |
| s03 的冲激周期 | 20.48 µs | `IMP_PERIOD=1024` / 50 MHz |
| 窗口里能装几个冲激 | **8 个** | 163.84 / 20.48 |

> 深度翻倍 = BRAM 翻倍。s02 实测：8192 × 74 位 ≈ 606 Kb ≈ **17 个 BRAM tile**。
> 所以"随手填大一点"是有代价的，够用就行（**至少要装下一个完整周期**，见 6.1）。

## 7. 采样格点：为什么 `sin=2047` 时 `cos` 不是 0

### 现象

ILA 上看到 `sin = 2047` 时 `cos = 38`；`cos = 2047` 时 `sin = -38`。
看起来像"正交错了"。

### 原理

`cos` 表是 `sin` 表移 1/4 圈：`cos[i] = sin[(i+1024) mod 4096]`。
设 `d` = 离理想峰值的地址数：

$$\cos[1024+d] \approx -3.14\,d \qquad \sin[d] \approx +3.14\,d$$

`cos = 38` → **d ≈ −12**；`sin = −38` 也算出 **d ≈ −12**。
**两次观测自洽** → 说明不是正交错了，只是**采样格点整体偏了约 12 个地址**。

**为什么偏 12**：地址每拍跳 8.19，理想峰值点（地址 1024）**压根没被采到**。
而正弦在**地址 1010~1037** 这 28 个表项上四舍五入后**都显示 2047** ——
很容易把"平坦顶部最左边那个采样点"误认为峰值。在那个点上 `cos` 还没降到 0。

### 正确的判据：`sin² + cos²`

**别去追"cos 必须等于 0"**（那是连续域的直觉，离散采样到不了）。

| 同一点的两个值 | 计算 |
|---|---|
| `sin=2047, cos=38` | 4190209 + 1444 = **4191653** |
| `cos=2047, sin=−38` | 一样，**4191653** |

理论中心 `2047² = 4190209`，**偏差 1444**。
判据（`tb_nco.v` 里用的）：**单边偏差 ≤ 4096**（12 位量化的理论上界 ≈2895，留了余量）。

**1444 < 4096 → 通过 ✅**

### 想看精确的峰值和零点

把 `FREQ_HZ` 降到 **≈12207**，地址步长变成 ≈1，**每个表项都会被采到**，
就能看到精确的 `2047` 和精确的 `0`。代价是窗口里只剩 2 个周期。

> **规律：数字信号里"某点的值"永远受采样格点影响。
> 判据要选对采样格点不敏感的（这里是 `sin²+cos²`），不要选"恰好等于某个值"。**

## 8. REQP-1839/1840：BRAM 地址带异步复位

### 现象

实现后的 DRC 里出现 20 + 20 条 warning：

```
| REQP-1839 | Warning | RAMB36 async control check | 20 |
| REQP-1840 | Warning | RAMB18 async control check | 20 |
```

原文（摘）：

> The RAMB36E1 `u_nco/fcos_o_reg_0` has an input control pin `.../ADDRARDADDR[10]`
> (net: `u_nco/sel[7]`) which is driven by a register (`u_nco/phase_acc_reg[27]`)
> that has an **active asynchronous set or reset**. This may cause **corruption of
> the memory contents and/or read values** when the set/reset is asserted and
> **is not analyzed by the default static timing analysis**.

### 原理

`phase_acc` 的复位是**异步**的，而它**直接驱动 BRAM 的地址脚**：

```verilog
always @(posedge clk or negedge rst_n) begin
    if (!rst_n) phase_acc <= 0;    // ← 异步复位，直接改变查表地址
    ...
end
```

复位一拉低，地址**异步**跳变，BRAM 读出的数据可能瞬时错乱，
**而且这段路径不参与静态时序分析**。

### ⚠️ 注意 `reset_sync` 并没有解决这条

`reset_sync` 实现的是"**异步**置位、**同步**释放"：
它同步的是**释放边沿**，**拉低那一刻仍然是异步的**。
所以 `phase_acc` 仍然带异步复位。

（`s00_blinky` 里"异步复位"看起来无害，是因为闪灯对一拍错值完全不敏感。）

### 什么时候会咬人

- 本设计**影响很小**：ROM 内容是上电配置时烧好的，异步复位不会改内容，
  最多读出一拍错值——而那一刻本来就在复位、输出也是 0。
- **但这是个模式**：以后写 FIFO、双口 RAM、或者任何"带异步复位的寄存器
  直接驱动存储器地址/控制脚"的设计，都会撞上这条。
- 要修就是把 `phase_acc` 改成**同步复位**。

### 同一类问题的第二个面：s03 的 DPOR-1（DSP 输出寄存器也用不上）

**2026-10-18 实测**：`fir.v` 的 `p_reg[]`（乘积寄存器）按仓库规矩用**异步复位**，
于是实现后的 DRC 报出 **486 条 DPOR-1**，报文说得很直白：

> `DSP u_fir/prod[10]` output is connected to registers with an asynchronous reset
> (`u_fir/p_reg_reg[10][0]`). This is preventing the possibility of merging these registers
> into the DSP Block since **the DSP block registers only possess synchronous reset capability**.

和 REQP-1839/1840 是**同一条原理**：**硬核（BRAM / DSP）内部的寄存器只认同步复位**。
带异步复位的触发器不能被"吸"进 DSP48 的输出寄存器，只能在外面另起一排。

| 这条的代价 | |
|---|---|
| 寄存器数量 | 每级乘积多一组外部触发器（s03 布局后 3242 个，其中很大一部分是这个） |
| 性能 | DSP 内部那条"最短路径"没用上；但 s03 实测 WNS 仍有 **+10.273 ns**（周期 20 ns），**根本没疼** |
| 功能 | **零影响** —— 不是错误 |

**所以要不要改？** 现在**不改**：50 MHz 下余量过半，改同步复位是"用真金白银的验证工作
换一个用不上的优化"。等将来时钟提到 100 MHz 以上、或者 s05 链路里 DSP 更紧张时再考虑 ——
那时候要改的是 `fir.v` 的复位策略，**并且 `make sim` 得重跑**（异步复位行为有专门的断言）。

> 这类"DRC 警告多但完全不影响功能"的条目，判断标准永远是**时序报告**：
> WNS ≥ 0 就没必要为了消警告去动 RTL。

## 9. 工程环境坑

### 9.1 Vivado 自带的文本编辑器不认 UTF-8

**用它编辑仓库里的 `.v` / `.xdc`，中文注释会被写坏**（变成 `相位累加器位�?` 这种），
文件不再是合法 UTF-8。

**2026-10-17 又踩了一次**：为了把 `mixer_top.v` 的 `CONJ` 由 1 改成 0，
在 Vivado 编辑器里改了一个参数，整个文件 **164 处中文字符**变成了替换字符。
逻辑（Verilog 本体）没坏，注释全毁 —— 但 `git diff` 变成了几十行噪音，
一眼看不出"到底改了什么"。

**怎么发现**：`git diff` 里出现 `�?` 就知道中招了。
批量扫描：在 PowerShell 里数 `U+FFFD`（`[char]0xFFFD`）的出现次数。
**怎么修**：`git checkout <改坏之前的提交> -- <文件>`，然后用 VS Code 重新改那一行。

后果：git diff 一片乱、Mac 那边读不了、`grep` 失效。

> **规矩：仓库里的源文件只在 VS Code（UTF-8）或让 AI 改。**
> 非要在 Vivado 里改，就**别碰带中文注释的行**。
> 改参数这种只动一个数字的事，**更不值得进 Vivado 编辑器** —— 一个字的改动
> 换来 164 个字符的损坏，纯亏。

顺带：Vivado 保存文件还会把行尾改成 **CRLF**（仓库统一 LF）。
`.gitattributes` 会自动规范化，但会造成无意义的 diff 噪音。

### 9.2 改完设置一定要 **Reset Synthesis**

Vivado 会缓存 run。改了 synthesis 设置（比如宏定义）之后，
**要 Reset Synthesis 再 Run**，否则可能在跑缓存的结果——
于是"我明明改了，怎么还是老样子"。

**怎么确认**：看 `<run>.runs/synth_1/<top>.tcl` 里 `synth_design` 那一行（见 2.A）。

### 9.3 Vivado 会把调试配置**写进你仓库里的 XDC**

因为工程是"**按路径引用**"约束文件（不是拷贝一份），
Set up Debug 之后 Vivado 会把 `create_debug_core ...` 一整段**追加到 `nco.xdc` 末尾**。

- 好处：Reset Synthesis 后 ILA 自动重建，不用重走 Set up Debug。
- 代价：**调试脚手架进了版本库**，里面写死了网名（`clk_IBUF_BUFG` / `fsin_o[*]`），
  设计一改就可能对不上 → 该在提交前删掉。

### 9.4 两台机器的分工是**现实约束**，不是偏好

**Vivado 只有 Windows / Linux x86-64 版，没有 macOS 版。**
所以 Mac 上写 RTL + 跑 `make sim`，Windows 上综合/实现/上板。

**Windows 这台机器上没有 iverilog / make**（`tools/` 被 gitignore，Mac 编译的那份不会跟过来），
所以**在 Windows 上改 RTL 等于没法验收**。

> **推论：在 Windows 上只改"不需要仿真验收"的东西**（XDC、文档、工程设置）；
> 真要动 RTL，要么回 Mac 跑 `make sim`，要么明确标注"未验收"。

可用的中间手段：Vivado 自带的 **`xvlog`** 只做**语法解析**（秒级，不是综合），
能挡住拼写/语法错误，但**挡不住行为错误**。它不能替代 `make sim`。

```powershell
# 语法检查（在临时目录跑，避免污染仓库）
& "C:\Xilinx\Vivado\2020.2\bin\xvlog.bat" --nolog -i tb -i rtl\common `
    rtl\common\*.v s01_nco\rtl\*.v s01_nco\tb\tb_nco.v
```

⚠️ **多个 TB 要分开调用**：`tb_common.vh` 有 include guard，
塞进同一次 xvlog 调用时第二个 TB 的 include 会被挡掉，报假的
`tb_errors is not declared`。

### 9.5 一个"检查方法本身有 bug"的例子

上面 9.4 那条就是：第一次把所有 TB 塞进一次 xvlog，
`tb_nco_top.v` 报了 20 个 `tb_errors is not declared` —— 看起来像代码坏了，
其实是**检查工具用错了**。

> **规律：工具报错时，先问一句"是不是我用的方式不对"。**
> 特别是"同一类文件里只有某一个报错"这种模式，通常指向调用方式而不是代码。

## 10. 参考模型和 RTL 犯了同一个错（s02 复数混频）

### 现象

`mixer.v` 的 `CONJ=1`（下变频）第一版是这么写的：

```verilog
wire signed [SUM_W-1:0] i_sum = ic_x - qs_x;                       // i*cos - q*sin
wire signed [SUM_W-1:0] q_sum = qc_x + (CONJ ? -is_x : is_x);      // q*cos ∓ i*sin
```

也就是说只翻了 Q 路那一项的符号。

验收向量是用 Python 参考模型生成的，而**那个参考模型犯了同一个错误**：

```python
i_sum = i * c - q * s
q_sum = q * c - i * s if conj else q * c + i * s      # 同样只翻了 q 路
```

结果：1617 个用例的向量回放**全绿**。

真正把它揪出来的是 `tb_mixer.v` 里一条手算的断言：

```verilog
// cos=0, sin=64, i=q=64 → 下变频的 i_out 应该是 i*cos + q*sin = +64
`check_eq("...", b_oi, 8'sd64);
```

实测 `b_oi = -64`。差一个负号。

### 原理

复本振混频只有两种，区别是乘 `e^{+jφ}` 还是 `e^{-jφ}`：

```
(i + jq)(cos + j sin) = (i·cos − q·sin) + j(i·sin + q·cos)     上变频
(i + jq)(cos − j sin) = (i·cos + q·sin) + j(q·cos − i·sin)     下变频
```

**"取共轭"是虚部整体取反**，所以 `j` 出现的那两项（`−q·sin` 和 `+i·sin`）
**都要翻**。只翻一项得到的东西既不是上变频也不是下变频，是第三种东西。

### 为什么这事值得单独记一条

**参考模型和 RTL 同源，就只能验证"实现和推导一致"，验证不了"推导对不对"。**

这类错误在验证里叫**共模错误**，向量回放对它天生免疫：
DUT 和参考模型就像两台用同一本错课本复习的考生，答案一模一样，一起错。

工业界的三种对策，缺一不可：

| 对策 | 在本仓库里长什么样 |
|---|---|
| 参考模型**换人 / 换语言 / 换工具**写 | Python 参考模型（任意精度整数，完全不碰 Verilog 位宽规则） |
| 补**性质断言**——不依赖具体数值的不变量 | 单位幅度本振下 `i²+q²` 不变；`i_out` 峰值处 `q_out≈0`；零输入出零 |
| 补**边界手算**——人能一眼核对的数值 | tie 点的舍入、±饱和、`CONJ` 方向 |

> **规律：一个测试用例的价值，不在于它跑了多少数据，而在于"它凭什么说期望值是对的"。**
> 数据量再大，也大不过一个"期望值本身可信吗"的问题。

### 同一批里还有两个同类的坑

**① 越界输入会被静默截位。**
`IW=8` 的配置里混进了 `i=511` 这种 8 位装不下的输入（生成器把"本振满幅"错当成了
"输入满幅"，`IW≠AW` 时就出事）。RTL 老老实实取低 8 位，测试照样绿。
**现在生成器里有 `assert`，`tb_mixer.v` 里还有一条"输入字段必须装得进端口位宽"的检查。**

**② `$readmemh` 读不到文件不报错（第 1 节那条）在向量回放里同样会咬人。**
所以向量文件的第 1 个字是哨兵 `C0FFEE01`，TB 第一条断言就查它。

> **共同点：这三种错误全是"静默"的 —— 不报错、不告警、结果看起来很正常。**
> 数字设计里最贵的不是报错，是**不报错**。凡是"读外部文件 / 隐式截位 / 隐式符号转换"
> 的地方，都要加一条显式的自检。

### 定点混频里的三件事（顺便记住）

1. **位宽**：全精度和是 `IW+AW+1` 位（`IW=AW=12` 时 25 位）。
   `(-2048)×(-2048)×2 = 2^23`，24 位补码最大只到 `2^23−1`，所以真的需要第 25 位。
   **先全精度算，最后才截**。
2. **增益**：定点相乘会把尺度平方，所以要右移 `SHIFT` 归一化。
   两个 `1.0 = 2^(W−1)−1` 的数相乘，"1.0"变成了 `2^(2W−2)`；
   右移 `AW−1` 位正好除回去（单位增益）。取小了会饱和削顶，取大了白丢精度。
3. **舍入与溢出**：右移是"向 −∞ 取整"，会给输出带来约 −0.5 LSB 的直流偏置；
   加半个 LSB 变成四舍五入，但**最大正值可能刚好顶出上界**，
   所以先把和加宽 1 位再舍入，最后**饱和**（不能回绕 ——
   回绕会让削顶处突然翻符号，是定点设计最经典的事故）。

## 11. 在网表里删 ILA：探针没了，逻辑也跟着没了

**事由**（2026-10-17 实测，s01 想补一份"无 ILA"基线）：没改 XDC，
直接在 Vivado 里 `Open Synthesized Design` → 选中 `u_ila_0` 删除 → 保存 →
增量实现重跑。报告出来了，看起来"资源健健康康变小了"。**实际上是设计被裁掉了。**

| 指标 | 综合输出的设计 | 这次实现出来的东西 |
|---|---|---|
| BRAM 推断（`synth_1/runme.log`） | `fsin_o_reg` 4096×12、`fcos_o_reg` 4096×12 → RAMB36×2 + RAMB18×2 = **3 tile** | **1 个 RAMB18 = 0.5 tile** |
| Slice LUTs | — | **14** |
| Slice Registers | — | 34 |
| 时序端点 | — | **76**（有 ILA 那版 4066） |
| DRC 里提到的 RAM | — | **只有** `u_nco/fsin_o_reg_1` 一个 |

### 为什么会这样（三步，每一部都可以从代码读出来）

1. **`fcos_o` 在板级顶层唯一的消费者就是 ILA。**
   `nco_top.v` 里 `led[0] = fsin_o[11]`、`led[3:1] = fsin_o[10:8]` ——
   `fcos_o` 一根引脚都没接。RTL 注释里那句 `keep = "true"` 存在的
   全部理由，就是"别把 cos 这路优化掉"。
2. **`keep` 是*综合*属性，不是*实现*属性。**
   在网表里把 ILA 删掉之后，`fcos_o` 立刻变成没有负载的网；
   实现阶段的 `opt_design` 按"无用逻辑"把它扫了 ——
   日志里 `24 netlist objects are constrained preventing optimization`，
   挡不住全部。
3. 于是：**cos 整张表消失，sin 表被裁到只剩 LED 用的 4 位**
   （`fsin_o[11:8]`）= 4096×4 = 16 Kb，正好塞进**一个 RAMB18**。

### 它为什么危险：板上看不出来

留下来的那 4 位**正是驱动 LED 的那 4 位**。所以这份比特流烧进去，
灯照样闪、符号位照样翻 —— 肉眼看"一切正常"。
被删掉的是 `fcos_o` 和 `fsin_o[7:0]`，它们**本来就不接引脚**，
唯一能看见它们的仪器是 ILA，而 ILA 已经被你删了。

> **这是最坏的一类 bug：错误被"删除"这个动作本身掩盖了。**
> 想穿它只需要一眼：`report_utilization` 里 Block RAM 数量。
> 一个"有两张 4096×12 表"的设计，Block RAM Tile 不可能是 0.5。

### 对照实验：干净重跑一遍，结论更狠

上面那次"网表里删 + 增量实现"有两种解释：要么 `keep` 不管用，要么是**增量实现 / 手改网表**
把流程搞脏了。为了分开这两件事，又做了一次**干净**的：XDC 里已经没有 ILA 了
（Vivado 自己删的），`Reset Synthesis` → `Run Synthesis` → `Run Implementation`，
日志第一行确认走的是 `link_design -top nco_top`（正常全流程，**不是增量**）。

| 指标 | 综合后 | 布局后（干净重跑也一样） |
|---|---|---|
| Block RAM Tile | **3**（`fsin_o_reg 4096x12` + `fcos_o_reg 4096x12`） | **0.5**（只剩 1 个 RAMB18） |
| Slice LUTs | 24 | 14 |
| Slice Registers | 34 | 34 |

**结论：`keep` 只保住了综合，保不住实现。** 干净流程照样把 cos 通路裁掉。

| 做法 | 结果 |
|---|---|
| 删 XDC 里的 `create_debug_core` 段 + `Reset Synthesis` | ✅ 综合报告是 **3 tile**（`keep` 在综合阶段确实生效） |
| 接着 `Run Implementation` | ❌ 布局后仍是 **0.5 tile** —— `opt_design` 不认 `keep` |
| 在网表里删 `u_ila_0` + 增量实现 | ❌ 同上，而且流程更脏（还会静默改写 XDC，见下） |

**所以"无 ILA 的 s01 资源基线"只能取自综合报告**（24 LUT / 34 Reg / 3 BRAM），
最终存进了 `logs/s01_nco/no_ila/`。

> `keep`（RTL 属性，综合阶段）≠ `DONT_TOUCH`（XDC 属性，实现阶段也认）。
> 想让 cos 表活到布局之后，得写
> `set_property DONT_TOUCH true [get_cells u_nco/fsin_o_reg*]`。
> 这次没做，因为"没有 ILA 的 s01"本来就没人需要 cos 通路。

**教训一句话：`keep` / `mark_debug` 这类属性属于"综合阶段"，事后从网表里删东西
等于改掉了综合时算好的语义。** 想得到"某个设计变体"的资源数，永远从**源文件/约束**
出发重跑一遍，别在中间产物上动刀 —— 而且要**看清楚取的是综合报告还是实现报告**。

### 附带发现：Vivado 会**改写你的约束文件**（连空格都改）

删完 ILA 之后，`s01_nco/constr/nco.xdc` 在没人编辑的情况下变了（文件时间
18:59:15，正好是那次操作的时刻）。`git diff` 显示两类改动：

1. 那 22 行 `create_debug_core … / connect_debug_port dbg_hub/clk` **整段消失**；
2. 几行 `set_property` 里 `R4  IOSTANDARD` 的**双空格被规范成单空格**。

原因：工程是**按路径引用**这个 XDC 的（不是拷贝一份进工程），
所以 Vivado 在"保存调试配置"时会直接把文件写回去。**这提醒两件事**：

- **调试脚手架一进 XDC，XDC 就变成"工具和我共同所有"的文件。**
  提交前最好看一眼 `git diff`，不然会以为是自己手滑。
- **改 XDC 之前先确认 git 干净。** 这次的 `git checkout` 兜底之所以能成立，
  就是因为动手前工作区是干净的。

> 顺带：这次还发现**"增量实现"到底用的是哪份检查点**很不直观 ——
> `impl_1/runme.log` 开头是 `open_checkpoint …/impl_1/nco_top.dcp`
> 而不是 `synth_1/` 的产物，日志里还写着 `Incremental flow is disabled`。
> 出现"我明明重新综合了，资源数却没变"时，**先看这一行**，
> 确认实现吃进去的到底是哪份网表。

### 顺手学到的排查招式：两份资源报告互相打架就说明中间被改了

**"实现后的资源数 vs 综合后的资源数"对不上，就是设计在中间被改了。**
`report_utilization` 在 `synth_1` 和 `impl_1` 各有一份
（`*_utilization_synth.rpt` / `*_utilization_placed.rpt`），
两份一比，BRAM / LUT 数量的差异会立刻把这种"静默退化"顶出来。
这次就是靠 3 tile → 0.5 tile 发现的。

## 12. FIR：先加后乘、系数和 = 2^(CW-1)、以及一个会撒谎的 TB

s03 是第一个"真正的硬骨头"：卷积、系数设计、对称优化、流水线、位宽预算全压在一个模块里。
这里记五件最值得带走的事。

### ① 对称抽头不是优化，是线性相位白送的

窗函数法设计出来的低通天然满足 `c[k] = c[N-1-k]`，这叫**线性相位**：
所有频率的群延迟都是 `(N-1)/2` 个采样，波形不会被滤"歪"。

对称还白送一个结构优化：

```
y[n] = sum_{i=0}^{H-1} c[i] * ( x[n-i] + x[n-(N-1-i)] )   (+ 中心抽头)
```

**先加后乘**。N=47 时乘法器从 47 降到 24（23 对 + 1 个中心）。
Artix-7 上 DSP48 是紧俏资源，这一下省掉一半；而且 DSP48 内部本来就有
pre-adder，所以一对预加 + 乘通常还是 1 个 DSP。

代价：关键路径变成"预加 + 乘"，但预加只有一个 13 位加法器，比省下来的
24 个乘法器划算得多。

### ② 系数和必须等于 `2^(CW-1)`，不是 `2^(CW-1)-1`

这是 s03 最容易想错的一个数。Q1.15 里 `1.0` 对应 `2^15 = 32768`，
低通的直流增益是 `sum(h) = 1`，所以量化后的系数和应该**恰好是 32768**。

照着"补码最大正数 = 2^(W-1)-1"写成 32767 的后果：

- 直流增益变成 `32767/32768 = 0.99997`，常数输入经过滤波器后**少 1 LSB**；
- 测试没法写"稳态输出逐位等于输入"，只能给容差；
- 这个 1 LSB 会随着级联（s05 的 DUC 里有好几级）累积。

做法：量化误差全部塞给中心抽头，让和精确等于 32768。奇数抽头只动中心，
对称性不变；偶数抽头把误差均分给中间两个（误差为奇数时会有 1 LSB 的不对称，
生成器会警告）。

> 这和 s02 的 `SHIFT=AW-1` 是同一件事的两面：
> **定点设计里"1.0 到底等于几"必须先定死**，后面所有增益预算都从它推出来。

### ③ 位宽链：为什么不是"乘完就截"

`mixer.v` 是"全精度乘加 → 舍入 → 饱和"，FIR 只是把"两个乘积"换成"24 个乘积"，
原则完全一样，但位宽链更长：

| 量 | 位宽 | 怎么来的 |
|---|---|---|
| 预加和 `PA_W` | 13 | 两个 12 位有符号数相加 |
| 单个乘积 `PROD_W` | 29 | 13 位 × 16 位 |
| 乘积和 `SUM_W` | 35 | 24 个 29 位相加，多 5 位，再留 1 位给舍入 |
| 最终 `FINAL_W` | 36 | 加半个 LSB 可能顶出 SUM_W |
| 输出 `OW` | 13 | 单位增益，多留 1 位余量 |

**为什么不在中间截？** 省不下 DSP —— 乘法器本来就是 13×16 这么大，
截中间结果只会白丢精度，而且会让"哪一位代表什么"变得很难查。

**为什么加法树要分组打拍？** 24 个 35 位加法如果在一个周期里做 5 层，
50 MHz 下也许能过，但余量会被吃掉；分成"组内 3 层 + 组间 2 层"后每级只有 3 层左右，
代价只是延迟从 2 拍变 4 拍。FIR 在数据通路里，4 拍延迟完全可以接受。

> 顺带记住：**延迟是设计参数，不是越小越好**。先把时序余量买回来，
> 再在链路预算里把这 4 拍算进去。

### ④ TB 也会撒谎：冲激没回 0，看到了"像模像样"的阶跃响应

写 `tb_table_binding.v` 时踩了一个很典型的 testbench bug：

```verilog
@(negedge clk);
x_in = 12'sd2047;        // 以为这是"一个冲激"
for (i = 0; i < 5; i = i + 1)
    @(negedge clk);
check(y_out == 128);     // 期望 h[0]
```

**忘了把 `x_in` 拉回 0**。于是送进去的是**阶跃**，输出是阶跃响应，
在那一拍正好是 `2047*(c0+c1)/2^15 = 640`。断言报 `y_out=640 128=128` 才发现。

为什么危险：640 这个数**看起来完全合理**（有符号、量级也对），
如果只检查"输出非零"或者肉眼看波形，就会以为通过了。

教训：

- **冲激测试必须显式写"下一拍回 0"**，而且最好检查**整段响应**（h[0..N-1]），
  不要只抽一个点；
- 所以 `tb_fir.v` 的冲激测试会核对全部 47 个抽头 + 对称性 + 两端回零；
- **testbench 的时序约定要写死**：s03 用的是"下降沿驱动、同一个下降沿读，
  第 k 个下降沿的输入对应第 k+4 个下降沿的输出"（4 级流水）。
  差一拍时 bug 可能只表现为"某个系数对不上"，很难从波形反推。

> 和 s02 的"参考模型和 RTL 犯同一个错"是同一类问题的两个面：
> **测试本身的错误不会让测试变红，只会让它测别的东西。**

### ⑤ 配套文件是"成套"的：用头字把它们绑在一起

s03 的参考向量头里有 9 个字：哨兵、场景数、样本数、数据行数、`IW`、`OW`、
`SHIFT`、`ROUND`、**系数校验和**。TB 回放前先逐条对一遍。

这是被 s02 的教训逼出来的：向量、系数、RTL 参数是**成套**的，
只改一个不重新生成，仿真要么失败得莫名其妙，要么"回放全绿但测的是旧滤波器"。
校验和只是一个 32 位滚动和（`h = h*33 + (c & 0xFFFF)`），不是密码学哈希，
但足够抓"改了 `coef.mem` 忘了 `make fir-vec`"。

> 同理，`$readmemh` 的数组长度必须和文件字数**恰好相等**（已知坑 9）。
> **所有 `$readmemh` 的失败方式都是静默的**，所以每次用它都要配一条自检。

## 13. Vivado 2020.2：宏在 More Options 里传 `-verilog_define`，不是勾 Name/Value

> **2026-10-18 实测定案（s03 上板第一次综合就撞上）。**
> 结论先说：**在 2020.2 工程里给 RTL 传宏，就是把
> `-verilog_define 宏名="值"` 整串写进
> Settings → Synthesis → **Options → More Options**。**
> 这里的内容会被**原样拼到 `synth_design` 的命令行**上 ——
> 它只是"多出来的命令行参数"，**不是**"宏名 + 宏值"两个字段的对话框。

### 现象：报 `Too many positional options`

More Options 里只写了宏本身、没写 `-verilog_define`：

```
FIR_COEFDIR="D:/Backup/Documents/GitHub/fpga-lab/s03_fir/lut/"
```

综合 2 秒就退，日志里是：

```
Command: synth_design -top fir_top -part xc7a100tfgg484-2 \
         FIR_COEFDIR="D:/…/s03_fir/lut/D:/…/s03_fir/lut/"
ERROR: [Common 17-165] Too many positional options when parsing
       'FIR_COEFDIR="D:/…/s03_fir/lut/D:/…/s03_fir/lut/"', please type 'synth_design -help' …
```

注意报错里那串路径**出现了两次**：`…/lut/D:/…/lut/` —— 那是另一个错
（粘了两遍），只不过被这个更早的错误先挡住了。

### 原理：More Options 是"命令行尾巴"，不是"宏填写框"

`synth_design` 的所有参数都是 `-选项 值` 的形式。你把 `FIR_COEFDIR="…"`

换句话说：**Vivado 不会"看着像个宏名就自动帮你补 `-verilog_define`"。**

### 正确写法（对照已经上板跑通的 s01）


**s01 的（已上板验证，可直接当模板）：**


差别只有宏名和路径。

### 证据链（Vivado 关着也能查，全在文件里）

|---|---|---|
| ① 工程设置 | `…\<工程>.xpr` | `<Option Id="MoreOptsStr">` 里的原文 |
| ② 实际命令行 | `…\<工程>.runs\synth_1\<top>.tcl` 第 108 行左右 | `synth_design …` 一整行 |
| ③ 报错 | `…\synth_1\<top>.vds` 或 `runme.log` | `ERROR: [Common 17-165] …` |

### 四个连带陷阱（每一个都会让你白跑一轮）

| # | 坑 | 后果 |
|---|---|---|
| 1 | 少了 `-verilog_define` | 🌟 立刻报错（**响的**，算运气好） |


① 有 `-verilog_define`　② 宏名对（`FIR_COEFDIR` / `NCO_LUTDIR`，别混）
③ **只有一个**路径　④ 结尾有 `/`

### 最后：宏生效了也不代表表读到了

宏只是"把绝对路径送进 RTL"。表到底进没进设计，还是要看第 3 节：
`report_utilization` 里 **DSP48E1 ≈ 24**（s03 的判据）。

## 14. 半带与多相：为什么 61 抽头只用 15 个乘法器

### ① 半带不是"又一种滤波器"，是"截止恰好 1/4 采样率"的必然结果

理想低通 `h[n] = 2f_c·sinc(2f_c(n-M))`，取 `f_c = 0.25`（归一化到采样率）：

```
h[n] = 0.5·sinc(0.5(n-M)),   M = (N-1)/2
```

`sinc(k) = sin(πk)/(πk)` 在**整数 k** 上恒为 0。所以只要 `n-M` 是偶数且不为 0，
`sinc` 就是 0 —— 再乘任何窗函数还是 0（窗值有限）。

```
h[M]     = 0.5          （窗在中心处 = 1）
h[M±2k]  = 0            （k = 1, 2, ...）
h[M±(2k+1)] ≠ 0         （只有奇数偏移非零，共 K = (N-1)/2 个）
```

**N = 61 → 只有 31 个非零抽头。** 这就是 s04 的 61 抽头表只写 30 行的原因：
中心的 0.5 不在表里，RTL 里写死 `2^(CW-2)`。

> 注意这不是"设计得刚好"：`f_c` 稍微偏一点，那些位置就不再是 0。
> 半带的"半"就是"通带 0..0.25、阻带 0.25..0.5 各占一半"，所以叫 halfband。

### ② 多相分解：把"2 倍速率上的一个卷积"拆成"1 倍速率上的两个卷积"

把 `H(z)` 按 2 拆开：

```
H(z) = Σ h[k] z^-k = Σ h[2i] z^-2i + z^-1 Σ h[2i+1] z^-2i
     = E(z²) + z^-1·O(z²)
```

`E` 是偶相（`h[0],h[2],…`），`O` 是奇相（`h[1],h[3],…`）。
半带给的是 `E(z) = 0.5·z^(-M/2)` —— **偶相就是一个延迟 + 乘 0.5**。

### ③ 插值：偶相恒等，奇相才要算

2× 插值 = 零插值（`u[2n]=x[n]`，`u[2n+1]=0`）再低通。输出在 2Fs 上：

```
y[2n]   = Σ_j h[j]·u[2n-j]     只有 j 偶数的项非零
        = Σ_i h[2i]·x[n-i] = h[M]·x[n-M/2]        ← 偶相只有中心
        ×2（补零插值的功率损失）= x[n-M/2]
```

`M/2 = 15`，所以 `y_e` 就是 `x` 延迟 15 个输入样本 —— **一个乘法器都不用**。

```
y[2n+1] = Σ_i h[2i+1]·x[n-i]    ×2
```

这就是 `interp2` 的全部：一条 30 拍延迟线、15 对预加 + 乘、一个加法树。

### ④ 为什么插值的 SHIFT 是 CW-2

系数按 Q1.15 设计，和 = 32768 = 1.0。插值要乘 2：

```
2·S / 2^15 = S / 2^14
```

所以 `SHIFT = CW-2`：**×2 不是多一级乘法，是少移一位**。
抽取没有零插值这一步，不需要补 2，所以还是 `CW-1`。
两个模块共用一张表，区别只有这一位 —— 这也是"一张表、两种用法"的由来。

### ⑤ 抽取：为什么 `x_o` 要多延迟一拍

交错信号 `u` 里 `x_e[n] = u[2n]`、`x_o[n] = u[2n+1]`（奇相**晚半个采样**）。
把 `j` 按奇偶拆开：

```
y[n] = Σ_j h[j]·u[2n-j]
     = Σ_i h[2i]·x_e[n-i] + Σ_i h[2i+1]·x_o[n-i-1]
                              └──────────────┘
                              k = 2i+1 → u[2n-2i-1] = u[2(n-i-1)+1]
```

那个 `-1` 不是笔误：奇相的窗口在 `x_o` 的下标里整体往回挪一格。
少写它，输出会整体错半个采样 —— 波形"看起来还在"，但每个点都差半个样本。

半带的偶相只有中心 → `Σ_i h[2i]x_e[n-i] = 0.5·x_e[n-15]`。
**这一项必须在移位之前加进和里**，否则会丢两次精度、舍入点变成两个。

### ⑥ 幅度互补：一条"结构性"的性质，量化破坏不了它

对任意对称半带，零相位幅度 `A(f)` 满足

```
A(f) + A(0.5-f) = 1
```

推导（用 `k-M` 的奇偶性）：

```
A(f) = Σ_k h[k]·cos(2πf(k-M))
A(f) + A(0.5-f)
     = Σ_k h[k]·(1 + (-1)^{k-M})·cos(2πf(k-M))
     = 2·Σ_{k-M 偶} h[k]·cos(...)
     = 2·h[M] = 1                （偶偏移只有中心）
```

关键在于**只有 `h[M]` 参与**，所以它对任意奇数抽头都成立 ——
量化、换窗、甚至手动改 `o[i]`，只要偶相还是"只有中心"，这条性质就严格成立。
`s04_resample/tb/tb_hb_coef.v` 用它做断言，残差 < 1e-6。

> 这条性质也解释了"插值再抽取"为什么通带干净：镜像落在 `0.5-f` 上，
> 它和主信号是互补的一对（`H + (1-H) = 1`）。

### ⑦ 资源账：省下来的到底是多少

| 设计 | 有效抽头 | 乘法器 | 备注 |
|---|---|---|---|
| s03 FIR | 47 | 24 | 对称折叠 23 对 + 中心 |
| s04 半带（单向） | 31 | **15** | 偶相 0 个 + 奇相 15 对 |
| s04 `resample_top` | —— | 30 | **两个方向都例化了**（实验台）；真实 DUC 只要插值那侧 |

所以看到 s04 的 DSP 是 30，别以为"半带没省"：**省的是每个滤波器**，
而实验台为了在板上一眼看完插值 + 抽取，装了两个。

### ⑧ 为什么不做 CIC / 通用 L/M

- **CIC** 适合大比例（>4）抽取，不需要乘法器，但通带下垂严重、要补偿滤波器。
  2× 用半带更划算（15 个乘法器已经很少）。
- **通用 L/M 多相** 参数化复杂，第一版做它会 80% 时间花在"下标怎么转"上，
  而不是"多相在干什么"。要 4× 就级联两级 2×（15×2 = 30 个乘法器），
  这比一个通用 4× 多相（约 30 个乘法器 + 复杂控制）工程上更常见。

## 15. s04 这轮踩的三个坑：都是"看起来对、局部全错"

### ① 拼接表达式是无符号的（最贵的一个）

```verilog
wire signed [PROD_W-1:0] prod_pas =
    {{1{e_dly[K/2][IW-1]}}, e_dly[K/2]} * HALF_COEF;   // ❌
```

`{...}` 是 unsigned，于是整个乘法按无符号算。负数输入变正数。

**症状极其规律**：正数用例全绿、负数用例全红。第一次跑 `tb_decim2` 时：

```
[FAIL] 直流 -1000：稳态输出 = -1000
[FAIL] 满幅 -2048：稳态输出 = -2048
[FAIL] 饱和不回绕：-2048 在 OW=8 上钳到 -128   （实际是 +127）
```

修法：先过一根 `wire signed`，让符号性由**赋值目标**继承（拼接本身不带符号）：

```verilog
wire signed [IW-1:0] e_tap = e_dly[K/2];
wire signed [PROD_W-1:0] prod_pas = e_tap * HALF_COEF;   // ✅
```

> 这和 s03 的 `wire signed [PA_W-1:0] pa = {{1{...}},xa} + ...` 是同一招。
> **教训**：测试必须正负都覆盖。如果只喂正数，这个 bug 会一路活着到上板。

### ② 级联的 LAT 是 8，不是 4

`tb_resample_top.v` 第一版按"每级 4 拍"的对齐去比对级联输出（`cap[k+3]`），
但插值 4 + 抽取 4 = **8**，应该是 `cap[k+7]`。结果整段响应平移 4 拍，
5 条断言全红，可数值本身"平移之后仍然是对的"。

**教训**：LAT 是 TB 的**约定**，不是设计的属性。改流水级数、改级联，
第一件事是把 TB 里的下标偏移跟着改。这种错不会让数值错，只会让位置错，
最容易误判成"设计坏了"。

> **同一个坑在 ILA 上会再犯一次。** TASK / XDC 里的 `k` 是输出下标（信号
> 意义上的 `y[k]`），而 ILA 的触发采样点就是 `cap[0]`。所以写 ILA 判读清单时
> 必须用 `cap[k+3]`（插值）或 `cap[k+7]`（级联），不能直接写 `k`。
> s04 的 TASK/XDC 第一版就漏了这一步：按 `k=15` 去找 `y_e`，会看到 0；
> 按 `k=30` 去找 `y_rt`（也就是 `cap[30]`），看到的是 `y_rt[23] = 37`，
> 不是 1991 —— 都是假故障。

### ③ 量化残差给错了抽头

`gen_hb_coef.py` 第一版把残差给了 `q[0]` —— 那是**最外侧**的抽头（30 LSB），
残差 -14 打上去变成 16，相对误差 87%。虽然绝对值小、频响几乎不动，
但这是"账算错了"，不是"精度取舍"。

改成两步：① 先把奇数抽头整体缩放，让浮点和恰好 = 0.25（残差只剩舍入噪声 ±几个 LSB）；
② 残差给**离中心最近**的那一对（最大的抽头，相对误差最小），而且成对修改，对称性不变。
现在残差是 0。

> 这和 s03 的"量化误差全塞给中心抽头"是同一条原则：
> **归一化的误差要放在最不敏感的地方，而且不能破坏对称性。**
