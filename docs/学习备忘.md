## 1. `$readmemh` 的相对路径一定失败

### 现象

- **iverilog**：表里全是 `x`，波形一片红，**不报错、不警告**。
- **Vivado 综合**：日志里两条 `CRITICAL WARNING`，然后**整个模块被优化掉**：

```
CRITICAL WARNING: [Synth 8-4445] could not open $readmem data file
  's01_nco/lut/sin.mem'; please make sure the file is added to project and
  has read permission, ignoring  [nco.v:23]
```

- **板上症状**：四颗 LED **全灭**（表全 x → 综合成常量 0 → `fsin_o = 0`）。

### 原理

**`$readmemh` 的路径是相对"仿真/综合进程的工作目录"，不是相对 `.v` 文件所在目录。**

- iverilog：`sim.sh` 里 `vvp` 在 `build/` 里跑 → 相对路径必然找不到。
- Vivado：run 目录是 `<工程>.runs/synth_1/`，由 `runme.bat` 里的
  `cd /d "%HD_SDIR%"`（`HD_SDIR` = runme.bat 所在目录）设定。仓库在别的盘/别的目录，
  所以 `"s01_nco/lut/"` 这种相对路径**永远对不上**。

### 怎么查

1. **看到"输出恒为 0 / 全灭"，先怀疑表**，而不是逻辑。
2. `report_utilization` 看 **`Block RAM Tile`**：表真进去了应该 > 0；是 0 就是没读到
   （详见第 3 节）。
3. Vivado 日志里搜 `8-4445` 或 `readmemh`。

### 结论（s01 实测）

| 做法 | 结果 |
|---|---|
| RTL 里写相对路径 `"s01_nco/lut/"` | ❌ 仿真、综合都读不到 |
| **把 `.mem` 加进工程 source** | ❌ **没用**（实测过。Vivado 报错里那句 "please make sure the file is added to project" 是**误导**——加进去它也不会去搜） |
| **`-verilog_define LUTDIR="<绝对路径>/"`** | ✅ **正确解法** |
| 把 `.mem` 拷到 run 目录下的 `s01_nco/lut/` | ⚠️ 能work但只是诊断手段，会造成"仿真/综合各用一份独立数据"，**别长期用** |

工程模式下的填法：**Settings → Synthesis → Options → More Options**：

```
-verilog_define LUTDIR="D:/Backup/Documents/GitHub/fpga-lab/s01_nco/lut/"
```

⚠️ **值里必须带真正的双引号**，**结尾的 `/` 不能少**（RTL 里是
``$readmemh({`LUTDIR, "sin.mem"}, rom)`` 拼起来的）。少引号会变成非法 Verilog。

## 2. 改了参数却没生效：顶层覆盖 + 一个字母

这是 s01 上板时**最贵的一个坑**，连续两轮综合+实现都白跑。

### 坑 A：改了底层模块的默认参数，但被顶层显式覆盖

```verilog
// nco.v
parameter integer FREQ_HZ = 100_000,   // ← 在这里改成 100 kHz

// nco_top.v
nco #(
    .FREQ_HZ(FREQ_HZ),   // ← 传的是 nco_top 自己的 FREQ_HZ = 1
) u_nco (...);
```

**只要顶层实例化时显式传了这个参数，底层模块的默认值就完全不起作用。**
改了等于没改，而且**没有任何报错**。

> **规律：模块的 `parameter` 默认值只在"没人覆盖它"的时候才生效。**
> 想改行为，要改**实际被传进去的那个值**——也就是顶层的参数，或者顶层实例化时写死的值。

**怎么查**：别猜，去看综合真正执行的命令行。Vivado 会把它写成
`<run>.runs/synth_1/<top>.tcl`：

```tcl
synth_design -top nco_top -part xc7a100tfgg484-2 -verilog_define LUTDIR="..."
```

宏定义、top、器件、任何 synthesis option 都在这行里，一目了然。

### 坑 B：宏名少一个字母

```tcl
-verilog_define LUDIR="D:/.../s01_nco/lut/"    ← 少了一个 T
```

RTL 里判断的是 `` `ifndef LUTDIR ``，于是判定"没定义"，走了兜底相对路径 →
回到第 1 节的坑。

**症状的特征**：报错信息里显示的路径是 **RTL 里的兜底路径**（`s01_nco/lut/sin.mem`），
而不是你填的绝对路径。**看到这个就说明你的宏压根没生效**，不用往下查了。

## 3. 怎么判断"表到底进没进设计"

**`report_utilization` 比日志更硬** —— 日志里的 warning 可能被淹没，资源报告骗不了人。

s01 实际数据对照：

| 指标 | 表**没**读进去 | 表读进去了 |
|---|---|---|
| `Block RAM Tile` | **0** | **3**（RAMB36×2 + RAMB18×2） |
| `Slice Registers` | **2** ← 只剩 `reset_sync` 的两个触发器 | **35** |
| `Slice LUTs` | 25 | 18 |
| 综合日志 | 2 条 `Synth 8-4445` | 0 条 |

**为什么表死了会连寄存器都没了**：表内容全 `x` → `fsin_o` 恒 `x`/0 →
下游（LED）是无所谓的 → 相位累加器、输出寄存器、ROM 全部变成 don't-care，
被综合**整块删掉**。所以"寄存器数少得离谱"本身就是"上游没数据"的信号。

> **一般化的教训**：资源用量比预期**少很多**，往往不是"优化得好"，
> 而是**有东西被优化没了**。先去查它该不该在。

顺便：日志里 `INFO: [Synth 8-7052] ... no optional output register could be merged`
说明 ROM 是满宽推断出来的（`fsin_o_reg | 4096x12 | Block RAM`），这行是有用的正面证据。

## 4. 有符号 vs 无符号：ILA 上 "∩ + ∪" 的经典症状

### 现象

ILA 抓出来的波形**不是正弦**，而是**一段开口向下、一段开口向上**（像个倒扣的碗挨着一个正放的碗）。

### 原理

NCO 的 ROM 是**12 位二进制补码**，取值 `-2047 … +2047`。
但 `nco.v` 的端口声明**没写 `signed`**：

```verilog
output reg [11:0] fsin_o,    // ← 位模式是补码，但类型是无符号
```

**位模式完全正确，丢的只是类型信息。** 而 ILA 按信号声明的类型选默认显示方式，
于是把负数映射成 `v + 4096`：

| 相位 | 真值（有符号） | 无符号显示 |
|---|---|---|
| 地址 0 | 0 | 0 |
| 地址 1024 | **+2047** | **2047** |
| 地址 2048 | 0 | 0 |
| 地址 3072 | **−2047** | **2049** |

画出来：
- 前半周期 `0 → 2047 → 0` = **∩（开口向下）**
- 后半周期 `0 →(跳) 4095 → 降到 2049 → 回到 4095 →(跳) 0` = **∪（开口向上）**

### 怎么解

1. **看波形**：ILA 里右键信号名 → **Radix → Signed Decimal**。
   （这本身就是验证：改完变正弦，就说明是显示问题而不是逻辑问题。）
2. **改代码**（s01 已做）：端口声明加 `signed`：

```verilog
output reg signed [AW-1:0] fsin_o
```

### 为什么这件事很重要（不是显示问题）

**`s02_mixer` 要做复数乘法。** 拿无符号端口去乘，正半周对、负半周全错——
**而且错得很隐蔽**。所以 `s01_nco/TASK.md` 最后那句"接口先想好"说的就是这个。

> **规律：模块边界的"有符号性"是一种接口约定，必须在接口上就表达清楚。**
> 内部 `reg signed` 一旦赋给无 `signed` 的端口，类型信息就在边界上丢了。

## 5. `mark_debug` 不够，要 `keep`

```verilog
(* mark_debug = "true" *)               wire [11:0] fcos_o;   // ← 不够
(* mark_debug = "true", keep = "true" *) wire [11:0] fcos_o;   // ← 这样才对
```

- **`mark_debug`**：只是给 Vivado 的 "Set up Debug" 向导看的**标记**，
  **不保证**阻止综合把这个网优化掉。
- **`keep`**：明确禁止综合优化掉这个网。

**s01 的实测后果**：`fcos_o` 没接到任何引脚（只给 ILA 用），
只写了 `mark_debug` 时，综合把 `fcos_o` 和 `fsin_o[7:0]` 这些"没接到引脚的位"裁掉了 ——
Set up Debug 的候选列表里**根本找不到这些网**。

> **规律：只要一个信号"不驱动任何输出引脚"，就要主动声明你想留住它。**
> 综合器没有理由替你保留。

## 6. ILA 使用要点（触发、窗口、开销）

### 6.1 先说最重要的：采样窗要装得下至少一个周期

ILA 用 `clk`（50 MHz）采样，缓冲深度只有几千点。
**8192 点 = 8192 × 20 ns = 163.84 µs。**

| `FREQ_HZ` | 周期 | 窗口内能看到 | 结果 |
|---|---|---|---|
| 1 | 1 s | 0.016% 个周期 | **一条直线** |
| **100 k** | 10 µs | **16.4 个周期**（每周期 500 点） | ✅ 光滑正弦 |

**所以看波形和看 LED 心跳是两次不同的 bitstream。**

### 6.2 ILA 核**不能写进 RTL**

它是 Vivado IP，iverilog 没有它的行为模型 —— 写进 `.v` 会让 `make sim` 直接编译不过。
正确做法：综合后用 **Set up Debug** 挂上去（它会写进 XDC）。

### 6.3 捕获窗是**以触发点为中心**的

ILA 是循环缓冲：触发命中后**再录半个窗口**才停。默认触发点落在窗口 **50%**。

所以"我触发在峰值，为什么波形不从峰值开始"——**峰值就在窗口正中**，
前半窗是触发**之前**录的数据。这是正常行为。

想改要动 ILA 核的 "Trigger position in window"，**得重新实现**——不值得为显示问题重跑。

### 6.4 为什么触发操作符里没有 rising edge

**边沿操作符只对 1 位信号出现。** ILA 的 probe 是**总线**（`fsin_o[11:0]`），
而 Trigger Setup **只能选整个 probe，不能切片**，所以只有比较类操作符。

真要边沿：加一个 1 位 probe，或者开 **Advanced Trigger**（`C_ADV_TRIGGER true`，
有 `$rise()` / `$fall()`）——**都要重跑实现**。

### 6.5 别用 `== 峰值` 当触发条件

**地址每拍跳 ~8.19**（`PHI_INC / 2^LUT_AW`）。表里 4096 个地址，一个周期只采到约 500 个，
**其余 ~3600 个根本不会被访问**。峰值 `+2047` 在表里**只有一个地址**（1024），
能不能踩上是碰运气。

**更稳的写法：用阈值。** 因为**正弦顶部很平**：

| 触发条件 | 覆盖地址范围 | 每周期命中 |
|---|---|---|
| `fsin_o == 7FF` | 只有 1024 | 平均 **1/8** 概率 |
| `fsin_o >= 7F0` | ≈ 945 ~ 1103 | 约 **19** 个采样点 |

### 6.6 为什么 `opt_design` 特别慢

加了 ILA 之后，`opt_design` 阶段要**现场生成并综合 `ila` + `dbg_hub` 两个 IP 核**：

```
Phase 1 Generate And Synthesize Debug Cores
  Generating Script for core instance : dbg_hub
  Generating Script for core instance : u_ila_0
```

s01 实测：`opt_design` **3 分 04 秒**，而 `place` 9 秒、`route` 39 秒。
**不是设计慢，是调试核的固定开销**，每次跑实现付一次。

顺带：`keep`/`mark_debug` 会让综合器"想优化但被拦住"，日志里能看到
`In phase Sweep, 889 netlist objects are constrained preventing optimization`。

### 6.7 调试开销有多大（s01 实测）

| 指标 | 无 ILA | 有 ILA | 开销 |
|---|---|---|---|
| Slice LUTs | 18 | **1117** | +1099 |
| Slice Registers | 35 | **1971** | +1936 |
| Block RAM Tile | 3 | **9** | +6 |
| BUFGCTRL | 1 | 2 | +1 |

**调试开销是设计本身的 60 倍** —— 正常，不用慌。

## 7. 采样格点：为什么 `sin=2047` 时 `cos` 不是 0

### 现象

ILA 上看到 `sin = 2047` 时 `cos = 38`；`cos = 2047` 时 `sin = -38`。
看起来像"正交错了"。

### 原理

`cos` 表是 `sin` 表移 1/4 圈：`cos[i] = sin[(i+1024) mod 4096]`。
设 `d` = 离理想峰值的地址数：

$$\cos[1024+d] \approx -3.14\,d \qquad \sin[d] \approx +3.14\,d$$

`cos = 38` → **d ≈ −12**；`sin = −38` 也算出 **d ≈ −12**。
**两次观测自洽** → 说明不是正交错了，只是**采样格点整体偏了约 12 个地址**。

**为什么偏 12**：地址每拍跳 8.19，理想峰值点（地址 1024）**压根没被采到**。
而正弦在**地址 1010~1037** 这 28 个表项上四舍五入后**都显示 2047** ——
很容易把"平坦顶部最左边那个采样点"误认为峰值。在那个点上 `cos` 还没降到 0。

### 正确的判据：`sin² + cos²`

**别去追"cos 必须等于 0"**（那是连续域的直觉，离散采样到不了）。

| 同一点的两个值 | 计算 |
|---|---|
| `sin=2047, cos=38` | 4190209 + 1444 = **4191653** |
| `cos=2047, sin=−38` | 一样，**4191653** |

理论中心 `2047² = 4190209`，**偏差 1444**。
判据（`tb_nco.v` 里用的）：**单边偏差 ≤ 4096**（12 位量化的理论上界 ≈2895，留了余量）。

**1444 < 4096 → 通过 ✅**

### 想看精确的峰值和零点

把 `FREQ_HZ` 降到 **≈12207**，地址步长变成 ≈1，**每个表项都会被采到**，
就能看到精确的 `2047` 和精确的 `0`。代价是窗口里只剩 2 个周期。

> **规律：数字信号里"某点的值"永远受采样格点影响。
> 判据要选对采样格点不敏感的（这里是 `sin²+cos²`），不要选"恰好等于某个值"。**

## 8. REQP-1839/1840：BRAM 地址带异步复位

### 现象

实现后的 DRC 里出现 20 + 20 条 warning：

```
| REQP-1839 | Warning | RAMB36 async control check | 20 |
| REQP-1840 | Warning | RAMB18 async control check | 20 |
```

原文（摘）：

> The RAMB36E1 `u_nco/fcos_o_reg_0` has an input control pin `.../ADDRARDADDR[10]`
> (net: `u_nco/sel[7]`) which is driven by a register (`u_nco/phase_acc_reg[27]`)
> that has an **active asynchronous set or reset**. This may cause **corruption of
> the memory contents and/or read values** when the set/reset is asserted and
> **is not analyzed by the default static timing analysis**.

### 原理

`phase_acc` 的复位是**异步**的，而它**直接驱动 BRAM 的地址脚**：

```verilog
always @(posedge clk or negedge rst_n) begin
    if (!rst_n) phase_acc <= 0;    // ← 异步复位，直接改变查表地址
    ...
end
```

复位一拉低，地址**异步**跳变，BRAM 读出的数据可能瞬时错乱，
**而且这段路径不参与静态时序分析**。

### ⚠️ 注意 `reset_sync` 并没有解决这条

`reset_sync` 实现的是"**异步**置位、**同步**释放"：
它同步的是**释放边沿**，**拉低那一刻仍然是异步的**。
所以 `phase_acc` 仍然带异步复位。

（`s00_blinky` 里"异步复位"看起来无害，是因为闪灯对一拍错值完全不敏感。）

### 什么时候会咬人

- 本设计**影响很小**：ROM 内容是上电配置时烧好的，异步复位不会改内容，
  最多读出一拍错值——而那一刻本来就在复位、输出也是 0。
- **但这是个模式**：以后写 FIFO、双口 RAM、或者任何"带异步复位的寄存器
  直接驱动存储器地址/控制脚"的设计，都会撞上这条。
- 要修就是把 `phase_acc` 改成**同步复位**。

## 9. 工程环境坑

### 9.1 Vivado 自带的文本编辑器不认 UTF-8

**用它编辑仓库里的 `.v` / `.xdc`，中文注释会被写坏**（变成 `相位累加器位�?` 这种），
文件不再是合法 UTF-8。

后果：git diff 一片乱、Mac 那边读不了、`grep` 失效。

> **规矩：仓库里的源文件只在 VS Code（UTF-8）或让 AI 改。**
> 非要在 Vivado 里改，就**别碰带中文注释的行**。

顺带：Vivado 保存文件还会把行尾改成 **CRLF**（仓库统一 LF）。
`.gitattributes` 会自动规范化，但会造成无意义的 diff 噪音。

### 9.2 改完设置一定要 **Reset Synthesis**

Vivado 会缓存 run。改了 synthesis 设置（比如宏定义）之后，
**要 Reset Synthesis 再 Run**，否则可能在跑缓存的结果——
于是"我明明改了，怎么还是老样子"。

**怎么确认**：看 `<run>.runs/synth_1/<top>.tcl` 里 `synth_design` 那一行（见 2.A）。

### 9.3 Vivado 会把调试配置**写进你仓库里的 XDC**

因为工程是"**按路径引用**"约束文件（不是拷贝一份），
Set up Debug 之后 Vivado 会把 `create_debug_core ...` 一整段**追加到 `nco.xdc` 末尾**。

- 好处：Reset Synthesis 后 ILA 自动重建，不用重走 Set up Debug。
- 代价：**调试脚手架进了版本库**，里面写死了网名（`clk_IBUF_BUFG` / `fsin_o[*]`），
  设计一改就可能对不上 → 该在提交前删掉。

### 9.4 两台机器的分工是**现实约束**，不是偏好

**Vivado 只有 Windows / Linux x86-64 版，没有 macOS 版。**
所以 Mac 上写 RTL + 跑 `make sim`，Windows 上综合/实现/上板。

**Windows 这台机器上没有 iverilog / make**（`tools/` 被 gitignore，Mac 编译的那份不会跟过来），
所以**在 Windows 上改 RTL 等于没法验收**。

> **推论：在 Windows 上只改"不需要仿真验收"的东西**（XDC、文档、工程设置）；
> 真要动 RTL，要么回 Mac 跑 `make sim`，要么明确标注"未验收"。

可用的中间手段：Vivado 自带的 **`xvlog`** 只做**语法解析**（秒级，不是综合），
能挡住拼写/语法错误，但**挡不住行为错误**。它不能替代 `make sim`。

```powershell
# 语法检查（在临时目录跑，避免污染仓库）
& "C:\Xilinx\Vivado\2020.2\bin\xvlog.bat" --nolog -i tb -i rtl\common `
    rtl\common\*.v s01_nco\rtl\*.v s01_nco\tb\tb_nco.v
```

⚠️ **多个 TB 要分开调用**：`tb_common.vh` 有 include guard，
塞进同一次 xvlog 调用时第二个 TB 的 include 会被挡掉，报假的
`tb_errors is not declared`。

### 9.5 一个"检查方法本身有 bug"的例子

上面 9.4 那条就是：第一次把所有 TB 塞进一次 xvlog，
`tb_nco_top.v` 报了 20 个 `tb_errors is not declared` —— 看起来像代码坏了，
其实是**检查工具用错了**。

> **规律：工具报错时，先问一句"是不是我用的方式不对"。**
> 特别是"同一类文件里只有某一个报错"这种模式，通常指向调用方式而不是代码。
