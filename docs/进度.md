### s03_fir Mac 侧设计要点（2026-10-18）

**结构**：47 抽头对称 FIR，`y[n] = sum(c[k]*x[n-k]) >>> 15`。
对称折叠后 24 个乘法器（23 对 + 1 个中心），四级流水：

| 级 | 内容 | 位宽 |
|---|---|---|
| 1 | 输入寄存 + 延迟线 `x_r/dly[]` | 12 |
| 2 | 预加 + 乘法 → `p_reg[]` | 29 |
| 3 | 4 组部分和 → `gsum[]`（每组最多 6 个乘积） | 35 |
| 4 | 组间相加 + 舍入 + 右移 + 饱和 → `y_out` | 13 |

- 位宽链：`PA_W=13` → `PROD_W=29` → `SUM_W=35` → `FINAL_W=36` → `OW=13`
- **先全精度算完，最后才截**；舍入常数 `1<<(SHIFT-1)`，最后饱和（不回绕）
- 系数：Q1.15，**和 = 32768**（直流增益精确 1.0），中心 9810，最小 −1867
- 频率响应：通带 [0, 0.10] 纹波 **0.037 dB**，阻带 [0.20, 0.5] **55.7 dB**

**验证**（四层，不是重复劳动）：

| TB | 检查点 | 抓什么 |
|---|---|---|
| `tb_fir.v` | 35 | 向量回放（4 场景）/ 冲激响应 47 点 / 对称 / 直流 / tie / 饱和 / IW=8 |
| `tb_fir_coef.v` | 15 | 系数表本身：对称、和、中心峰、无 x、coef5 精确值 |
| `tb_fir_top.v` | 21 | 顶层：reset_sync 2 拍 / 冲激宽度与周期 / 响应峰值 613 / LED 心跳 / 异步复位 |
| `tb_table_binding.v` | 10 | NCO 表 + FIR 表同一轮仿真各自加载（`NCO_LUTDIR`/`FIR_COEFDIR` 回归） |

**反向验证（4 处，全部变红）**：

| 改坏 | 实际反应 |
|---|---|
| 系数下标 `coef[gi]` → `coef[gi+1]` | 12 条 FAIL（冲激 42 点、4 个向量场景、4 条直流…） |
| 关掉四舍五入 | 10 条 FAIL（向量 4 场景、25 个冲激点、中心 612、tie） |
| 饱和改成回绕 | 2 条 FAIL（正好是 OW=8 的正/负溢出检查） |
| 中心抽头 `dly[HALF-1]` → `dly[HALF-2]` | 11 条 FAIL（中心 0、对称 2 点、4 个向量场景、tie） |

> 饱和那条只有 2 条 FAIL，是**正常且有意义**的：主配置 OW=13 离饱和边界很远，
> 改坏了它没感觉。所以专门留了一个 `OW=8` 的实例来撞边界。

## 已知坑（踩过的，别再踩）

### 1. iverilog 13.0：字符串常量赋给向量会损坏非 ASCII 字节

把含中文的字符串常量赋给 `reg [N:0]` / 向量，只有部分字节写得进去，
其余位留成 x，`$display("%s")` 打出来是一堆乱码。

对照实验（都实测过）：

| 写法 | 结果 |
|---|---|
| `$display("%s", "level 稳定为 0")` | ✅ 正常 |
| `reg [8*40-1:0] m; m = "level 稳定为 0";` | ❌ 乱码 |
| 同上，但字符串用八进制转义 `"\347\250\263…"` | ❌ 照样乱码 |
| `m[319-:8] = 8'hE7; …` 逐字节赋值 | ✅ 正常 |

**所以 `tb_common.vh` 里的 `check` / `check_eq` 是宏，不是 task** ——
宏是文本替换，中文会原样落在 `$display` 的参数位置上，不经过向量。

**代价：调用时要写反引号，而且断言必须单独成行**（宏里有 `if/else`，
写成 `if (x) \`check(...); else ...` 会 dangling else）：

```verilog
`check(cond, "描述文字");
`check_eq("描述文字", actual, expected);
```

### 2. `$readmemh` 读不到文件时**不报错**，表里全是 x

`$readmemh` 的路径是相对**仿真/综合进程的工作目录**，不是相对 `.v` 文件所在目录。
`sim.sh` 里 `vvp` 是在 `build/` 里跑的，所以 RTL 里写 `"s01_nco/lut/sin.mem"`
这种相对路径**必然读不到** —— 而且不报错、不警告，ROM 里全是 x，波形一片红。

规避：`scripts/sim.sh` 会自动传**表目录宏**（绝对路径）。**2026-10-18 起一个表一个宏**：
NCO 的表用 `NCO_LUTDIR`，FIR 系数用 `FIR_COEFDIR`。RTL / TB 统一写成

```verilog
`ifndef NCO_LUTDIR
  `define NCO_LUTDIR "s01_nco/lut/"   // 兜底：手工跑 iverilog / Vivado 综合
`endif
initial $readmemh({`NCO_LUTDIR, "sin.mem"}, sin_rom);
```

> 旧的单一 `LUTDIR` 只在 `nco.v` 里作为兼容别名保留（旧 Vivado 工程不用改），
> **新代码不要再用它** —— 原因见「已知坑 8」。

细节见 `s01_nco/lut/README.md` 和 `s03_fir/lut/README.md`。

### 3. `tb_errors` 由 `tb_common.vh` 声明，testbench 里不要再写一遍

Verilog 要求先声明后使用。`include` 展开在模块开头，所以
`integer tb_errors = 0;` 必须写在几个断言**之前**。放在头文件里最省事。

### 4. `sim.sh` 必须带 `-I $ROOT/tb`

`tb_common.vh` 在 `tb/`，而各 stage 的 testbench 在 `s0x_xxx/tb/`，
只加 `-I $TBDIR` 找不到。

### 5. bash 3.2 + UTF-8：`$VAR` 紧跟中文字符会吃掉字符

macOS 自带的 `/bin/sh` 是 **bash 3.2（2007 年）**。在 UTF-8 locale 下，
`$VAR` **紧挨着**一个中文字符时，bash 会把那个中文字的字节当成
变量名的一部分，于是变量值和半个字一起消失。

实测（`T=4`）：

| 写法 | 输出 | 结果 |
|---|---|---|
| `echo "x$T个"` | `x` + 半个"个" | ❌ 丢了 `4` |
| `echo "x${T}个"` | `x4个` | ✅ |
| `echo "x$T 个"`（有空格） | `x4 个` | ✅ |
| `LC_ALL=C` 下 `echo "x$T个"` | `x4个` | ✅ |

**规律：变量展开后面直接跟非 ASCII 字符就会出事**，跟空格就没问题。

**症状很隐蔽**：不报错、退出码 0，只是那行字少了一两个字符，
看起来像"终端渲染问题"，很容易当成显示 bug 放过去。

**规避：变量一律写 `${VAR}`**（花括号明确边界，任何 locale 都对）。

排查方法：`命令 | hexdump -C` 看原始字节，别信终端渲染。

### 6. 每个 RTL 文件都要写 `` `timescale ``

少写一个，iverilog 会**从上一个编译的文件那里继承**过来，于是：

- `make lint` 打出 `timescale for nco inherited from another file`（编译顺序一变就变）；
- 单文件仿真时打 `Some modules have no timescale ...`。

现在 5 个 RTL 文件全部写了 `` `timescale 1ns/1ps ``，警告消失。
TB 里的断言和 `#延时` 都依赖 timescale，继承来的值不可控，所以这条不是洁癖。

### 7. 纯参数的计算不能放在 `always @(*)` 里（敏感列表是空的）

写 `always @(*) temp = FREQ_HZ << PHASE_W;`（右边全是 `parameter`）时，
**块里没有任何信号可敏感，iverilog 从头到尾不执行它** —— `temp` 一直是 `x`，
而且不报错。实测：`always @(*)` 版本 `temp=x`，改成 `localparam` 立刻算出正常值。

顺带把那句最容易传错的位宽规则说清楚（两种写法都实测过）：

| 写法 | 结果 | 原因 |
|---|---|---|
| `localparam integer X = FREQ_HZ << PHASE_W;`（32 位目标） | `1<<32` → **0** | 移位左操作数按上下文宽度 = 32 位 |
| `localparam [63:0] X = FREQ_HZ << PHASE_W;`（64 位目标） | `1<<32` → 4294967296 ✅ | 赋值目标的宽度会**反过来**加宽表达式 |

所以"左操作数不会因为右边是 64 位就被加宽"是**错的**：位数由**上下文**（赋值目标）决定。
真要稳，就直接写 `64'd1 << PHASE_W`，别依赖上下文推断。

### 8. 跨 stage 复用模块：`deps.txt` 与"一个表一个宏"

`sim.sh` 默认只编**本 stage 的 `rtl/` + `rtl/common`**。s02 的 `mixer_top` 里
例化了 s01 的 `nco`，于是 `make sim` 直接报 `Unknown module type: nco`。

解法：stage 目录下放一个 `deps.txt`，每行写一个依赖的 stage 目录名
（`s02_mixer/deps.txt` 里就一行 `s01_nco`）。`sim.sh` 会把它的 `rtl/*.v` 编进来。

**曾经的坑：`LUTDIR` 全仓库只有一个。** `nco.v` 里写死了
`$readmemh({`LUTDIR, "sin.mem"}, ...)`，而 `LUTDIR` 由 `sim.sh` 传，所以
**同一轮仿真里只能有一个查表目录**。s02 自己没有 `lut/`，`sim.sh` 沿着 `deps.txt`
找到 `s01_nco/lut`，正好对上；但 s03 有了自己的 `coef.mem` 之后，
如果同一轮里既例化 nco 又例化 fir，一个宏只能指一个目录 —— 必然有一个读错，
而且 `$readmemh` 读不到**不报错**。

**2026-10-18 已修：一个表一个宏。**
`sim.sh` 按"当前 stage + deps"逐个 stage 查 `lut/`，给语义宏：
`s01_nco → NCO_LUTDIR`，`s03_fir → FIR_COEFDIR`。新增带表的 stage 时，
在 `scripts/sim.sh` 的 `table_macro_for()` 里加一行，RTL 里用对应宏。
`tb_table_binding.v` 是这条的回归：同一轮仿真里同时例化 nco 和 fir。

**Vivado 侧同理**：s02 的工程用 `NCO_LUTDIR` 指 `s01_nco/lut/`；
s03 的工程用 `FIR_COEFDIR` 指 `s03_fir/lut/`。一个工程里两张表都要，
就两个宏都配。

### 9. `$readmemh` 的数组长度必须和文件字数**恰好相等**

给 `$readmemh` 的数组比文件**长** → 打 `Not enough words in the file for the requested
range [0:N]` 告警（不影响结果，但日志很脏，而且掩盖真正的问题）；
比文件**短** → 尾部被**静默截断**（只有一句告警，很容易淹掉）。

所以生成器（`gen_mixer_vec.py`）把所有向量文件**补齐到同一个长度**（`N_PAD = 1620`），
TB 那边 `VEC_MAX_CASES = 1620` 和它**成对**，并且有一条断言盯着
"用例数必须恰好等于数组容量"。改一个必须改另一个。

> 和「已知坑 2」（`$readmemh` 读不到文件不报错）是同一类问题的两个面：
> **`$readmemh` 的失败方式全是静默的**，所以每次用它都要配一条自检。

### 10. FIR 的系数和必须等于 `2^(CW-1)`，不是 `2^(CW-1)-1`

这是 s03 最容易想错的一个数。Q1.15 里 `1.0` 对应 `2^15 = 32768`，
低通的直流增益是 `sum(h) = 1`，所以量化后的系数和应该**恰好是 32768**。

有人会照着"补码最大正数 = 2^(W-1)-1"写成 32767。后果：

- 直流增益变成 `32767/32768 = 0.99997`，常数输入经过滤波器后**少 1 LSB**；
- 测试没法写"稳态输出逐位等于输入"，只能给容差；
- 更糟的是，这个 1 LSB 的偏差会随着级联（s05 的 DUC 里有好几级）累积。

我们的做法：量化误差全部塞给中心抽头，让和精确等于 32768。
奇数抽头只动中心，对称性不变；偶数抽头把误差均分给中间两个（误差为奇数时
会有 1 LSB 的不对称，生成器会警告）。

> 这和 s02 的 `SHIFT=AW-1` 是同一件事的两面：
> **定点设计里"1.0 到底等于几"必须先定死**，后面所有增益预算都从它推出来。

### 11. FIR 的位宽链：为什么不是"乘完就截"

`mixer.v` 是"全精度乘加 → 舍入 → 饱和"，FIR 只是把"两个乘积"换成"24 个乘积"，
原则完全一样，但位宽链更长：

| 量 | 位宽 | 怎么来的 |
|---|---|---|
| 预加和 `PA_W` | 13 | 两个 12 位有符号数相加 |
| 单个乘积 `PROD_W` | 29 | 13 位 × 16 位 |
| 乘积和 `SUM_W` | 35 | 24 个 29 位相加，多 5 位，再留 1 位给舍入 |
| 最终 `FINAL_W` | 36 | 加半个 LSB 可能顶出 SUM_W |
| 输出 `OW` | 13 | 单位增益，多留 1 位余量 |

**为什么不在中间截？** 因为省不下 DSP —— 乘法器本来就是 13×16 这么大，
截中间结果只会白丢精度，而且会让"哪一位代表什么"变得很难查。
**为什么加法树要分组打拍？** 24 个 35 位加法如果在一个周期里做 5 层，
50 MHz 下也许能过，但余量会被吃掉；分成"组内 3 层 + 组间 2 层"后每级只有 3 层左右，
代价只是延迟从 2 拍变 4 拍。FIR 在数据通路里，4 拍延迟完全可以接受。

> 顺带：对称预加让乘法器从 47 降到 24。**这是"线性相位"白送的结构优化**，
> 不是先设计完再想出来的 trick —— 窗函数法设计出来的系数天然对称。

### 12. TB 也会撒谎：冲激没回 0，看到了"像模像样"的阶跃响应

s03 写 `tb_table_binding.v` 时踩了一个很典型的 testbench bug：

```verilog
@(negedge clk);
x_in = 12'sd2047;        // 以为这是"一个冲激"
for (i = 0; i < 5; i = i + 1)
    @(negedge clk);
check(y_out == 128);     // 期望 h[0]
```

**忘了把 `x_in` 拉回 0**。于是送进去的是**阶跃**，输出是阶跃响应，
在那一拍正好是 `2047*(c0+c1)/2^15 = 640`。断言报 `y_out=640 128=128` 才发现。

为什么危险：640 这个数**看起来完全合理**（是个有符号的正数、量级也对），
如果当时只检查"输出非零"或者肉眼看波形，就会以为通过了。

教训：

- **冲激测试必须显式写"下一拍回 0"**，而且最好检查**整段响应**（h[0..N-1]），
  不要只抽一个点；
- 这也是为什么 `tb_fir.v` 的冲激测试会核对全部 47 个抽头 + 对称性 + 两端回零；
- **testbench 的时序约定要写死**：s03 用的是"下降沿驱动、同一个下降沿读，
  第 k 个下降沿的输入对应第 k+4 个下降沿的输出"（4 级流水）。
  差一拍时 bug 可能只表现为"某个系数对不上"，很难从波形反推。

> 和 s02 的"参考模型和 RTL 犯同一个错"是同一类问题的两个面：
> **测试本身的错误不会让测试变红，只会让它测别的东西。**
> 所以每个 stage 都要有"改坏 RTL 看测试变不变红"这一步。
