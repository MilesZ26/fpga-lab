### 装仿真器

```sh
make setup
```

`scripts/setup_tools.sh` 现在会：

1. 如果 `tools/iverilog/bin/iverilog` 已存在 → 直接跳过
2. 如果系统有 iverilog → 跳过
3. 有 Homebrew → `brew install icarus-verilog`
4. 都没有 → **源码编译进 `tools/`**（不写系统目录、不需要 sudo）
   - 先编译 **bison**（iverilog 的 `vhdlpp/parse.y` 用了 `%define api.pure`，
     而 **macOS 自带的 bison 是 2.3，2006 年的版本，报语法错误**）
   - 再编译 iverilog `v13_0`

**这一段是踩过坑的**：一开始只编 iverilog，挂在了 bison 上。见 `docs/进度.md` 的「已知坑」。

### 波形查看：用 Surfer，别用 GTKWave

**GTKWave 在 Homebrew 里已经被标记为 `disabled`**，上游也没提供可用的
macOS 二进制，`brew install gtkwave` 会失败。网上很多教程还在教这个。

改用 **Surfer**：Rust 写的，原生窗口，Apple Silicon 有现成二进制，不需要 X11。

```sh
brew install surfer
make wave VCD=build/tb_blinky.vcd     # make wave 会优先用 Surfer
```

### 关于 verilator

它的价值是更严格的 lint 和 SVA 断言支持 —— 属于"更好"，不是"必须"。
目前 `make lint` 用的是 iverilog，够用。想要它：`brew install verilator`。

### ⚠️ 限制：Windows 侧 DSH 的 shell 只在「完全权限」下可用

**症状**：会话文件策略为 `workspace-write` 时，DSH 调 `pwsh` 执行任何命令
都返回 **`0xC0000142`**，`echo hello` 也一样，而且**没有任何 stdout/stderr**
—— 进程根本没活到执行命令那一步。

**根因（2026-10-15 查定）：是 DSH 的 Windows 沙箱，不是这台机器的环境问题。**
该模式下 DSH 把子进程降级为 **Low 完整性受限令牌**，pwsh 在这套令牌下
**早期 DLL 初始化**就失败，所以连一行报错都吐不出来。DSH 自带源码注释
（`dsh-sandbox-windows-acl`）明确记载了这个失效模式：保活组缺失时
"早期 DLL 初始化会以 `0xC0000142` 死亡、CNG 会让 pwsh 以 `0xE0434352` 崩溃"。

**排查过程**（全部实测过，别再重走）：

| 假设 | 结论 |
|---|---|
| PowerShell 没装 / 装的是商店版 | ❌ 否。先装 MSIX 版、再装 MSI 版（`C:\Program Files\PowerShell\7\pwsh.exe`），症状一字不变 |
| `PATH` 是旧快照，DSH 找不到 pwsh | ❌ 否。彻底重启 DSH 后不变；且执行器本来就会自己探测 `C:\Program Files\PowerShell\7\` |
| 工作区文件权限（ACL）有问题 | ❌ 否。DSH 自带的 `diagnose-windows-sandbox-acl` 判定 **`NOT_THIS_CLASS`**：权限完整、无外来条目、**零改动** |
| **沙箱受限令牌** | ✅ **是。** 同一台机器、同一个 pwsh：沙箱内恒 `0xC0000142`，**切成「完全权限」后一切正常** |

**对策**：需要 DSH 跑命令时，**把会话文件策略设为「完全权限」(full access)**。

- ✅ `workspace-write` 下可用：读文件、写文件、grep、改 md
- ❌ `workspace-write` 下不可用：`make sim`、`make lint`、`git push/pull`、
  一切要开子进程的操作
- ✅ **「完全权限」下全部可用**（连 `git` 也能直接调）

> **命令行 git 现在可以直接用了**：Git for Windows 于 2026-10-15 装好，
> `C:\Program Files\Git\cmd\git.exe` 已在 PATH 上。
> 此前文档里记着"Git for Windows 已就位"其实不准确 —— 实测
> `C:\Program Files\Git` 当时并不存在，命令行 git 一直不可用。

### ✅ 实采版本：2020.2（2026-10-14 定，**已装好并验证可用**）

**结论：就用 2020.2。** 判据是"**能不能跑通**"，不是"官方怎么说"。

- 2020.2 的官方支持目标是 Windows 10（发布时 Win11 还不存在），
  但我们**不打开厂商工程、不用 IP**，社区实测它在 Win11 上可用
- 想去追"官方支持 Win11"的版本绕了一圈：**2025.2 的 web installer 不好用**，
  方案作废，代价是几十 GB 下载时间

> **教训**：Vivado 版本这件事的时间成本极高（40+ GB 下载）。
> 下次遇到"官方不支持但实际能用"的情况，**先花 10 分钟实测**，
> 别先下几十 GB 的东西。判据用"能不能跑通"。

参考：AMD 已把 7 系列生命周期延长到 **2040 年**，器件不会被砍。

### 装完必须自检（两道，都要）

**① 综合侧** —— 建工程之前，Tcl Console：

```tcl
get_parts xc7a100t*
```

返回空 = 安装时漏勾了 `7 series` / `Artix-7`，回去补装。

**② 下载侧** —— Hardware Manager → Auto Connect 能列出器件。

> `get_parts` 只验证综合侧，下载是**另一条独立的器件识别路径**，两者可能不一致。
> 下载报 `unsupported part` 时**不要改 RTL 和约束**，那是工具版本的问题。
> 两道都过就锁定版本，别再折腾。

> ✅ **2026-10-14：两道都已隐含通过。** 器件识别不出来的话，
> `Program Device` 根本走不到"下载成功"这一步，而板子上确实跑起来了。
> **所以版本验证完毕，以后不用再看这一节。**

## 目标开发板

- ✅ **已到货**，且**已实测上板成功**（2026-10-14）
- **Vivado 器件全名（建工程时选这个）**：**`xc7a100tfgg484-2`**
  —— 100T / **fgg484** 封装 / **-2** 速度等级。
  ⚠️ 封装必须这个：同为 100T，`csg324` 的引脚编号完全不同。

- 引脚约束（XDC）**必须对着原理图 / 厂商引脚表抄**，不能靠搜索或记忆猜
- 板级资料只用三样：**时钟频率 / 引脚、LED / 按键引脚、下载流程**
  —— 别跟着厂商教程的目录（LED → 按键 → UART → SDRAM → HDMI）一路学下去

> ✅ **板级层的使命已完成**：这三样资料全部拿到、写进
