# Mac ↔ Windows 同步指南

用 **git + Gitee（码云）** 在两台机器之间同步，**不要用网盘**。

> **2026-10-15 平台迁移**：远端主力从 GitHub 换成了 **Gitee**
> （`gitee.com/milesz26/fpga-lab`），认证方式用 **SSH**。
> 原来的 GitHub 仓库没删，改名叫 **`github`** 远端留着当备份 ——
> 但**它不会自动同步**，想让 GitHub 也更新得手动 `git push github main`。

---

## 总体结构

```
        ┌──────────────────────────┐
        │           Gitee          │  ← 中转站（远程仓库）
        │  gitee.com/milesz26/...  │
        └──────────┬───────────────┘
                   │
        push ↓     ↑ pull        push ↑     ↓ pull
                   │
   ┌───────────────┴──┐     ┌──┴────────────────────┐
   │   Mac（主战场）    │     │  Windows（Vivado 机）  │
   │  写 RTL / 跑仿真   │     │  综合 / 实现 / 上板    │
   │  改 rtl/ tb/ docs/ │     │  只往 logs/ 写东西     │
   └───────────────────┘     └───────────────────────┘
```

**关键分工（这条能让你几乎不会遇到冲突）：**

| 机器 | 只写这些目录 |
|---|---|
| Mac | `rtl/` `tb/` `docs/` `scripts/` `Makefile` |
| Windows | `logs/`、`docs/`（现在有 DSH 了，也能改文档）、必须在 Vivado 里改的 `constr/` |

两边不碰同一批文件，就不会有合并冲突。

> ⚠️ **`docs/` 是两边唯一重叠的目录**，而 `docs/进度.md` 又是两边都会改的文件 ——
> 这是现在**最可能出冲突**的地方。规矩很简单：
> **动手改 `docs/进度.md` 之前先 `git pull`，改完立刻 push 并让另一台 pull。**
> 不要两台机器各改半天再合。
>
> 另外：不要**同时**开两个 DSH 去改同一份文件（一个 push 完另一个还拿着旧内容）。

## 一次性设置

### A. 在 Mac 上

**1. 配置 git 身份**（只需一次；会写进每一个提交，永久可见）

```sh
git config --global user.name  "你的名字"
git config --global user.email "你的邮箱"
```

> 建议邮箱和 Gitee 账号用同一个 —— Gitee 的提交统计按邮箱匹配，
> 不一致的话贡献图上不会出现你的提交。

**2. 配 SSH 密钥**（一次配置，以后免密）

```sh
ssh-keygen -t ed25519 -C "mac-arm64-fpga-lab"
# 一路回车即可（密码短语可以留空）

pbcopy < ~/.ssh/id_ed25519.pub     # 把公钥复制到剪贴板
```

然后打开 Gitee → 右上头像 → **设置** → **安全设置** → **SSH 公钥** →
标题填 `mac-arm64-fpga-lab` → 粘贴公钥 → 确定。

> 标题只是给人看的标签，不参与认证。但**两台机器必须起不同的名字**
> （Windows 侧叫 `win11-fpga-lab`）—— 否则以后某一把要吊销时，
> 你在列表里分不清哪把是哪把。
>
> **密钥不要跨机器拷贝。** 每台机器自己生成一把，各自贴一份公钥到 Gitee。

验证：

```sh
ssh -T git@gitee.com
# 看到 "Hi 用户名! You've successfully authenticated" 就成功
# 第一次连接会问 yes/no，输入 yes 记住指纹即可
```

**3. 远端仓库已经存在，不用再建**

`gitee.com/milesz26/fpga-lab` 是从 GitHub 导入的，历史完整。
**所以 mac 上不需要"建仓库 + 首次推送"那一套**，只要把远端接上：

```sh
cd ~/Documents/fpga-lab

git pull                                  # 先和 GitHub 对齐，确认没落后
git remote rename origin github           # 旧远端改名为 github，留作备份
git remote add origin git@gitee.com:milesz26/fpga-lab.git
git fetch origin
git branch --set-upstream-to=origin/main main
```

> ⚠️ **两步的顺序不能反**：必须先 `rename` 再 `add`。
> `rename` 会自动把 `branch.main.remote` 由 `origin` 改写成 `github`；
> 反过来先 `add` 会撞名报错。

做完 `git remote -v` 应当看到：`origin` 指向 gitee，`github` 指向 github。

> **万一以后真要新建仓库**：**绝对不要勾** "Add a README" /
> "Add .gitignore" / "Choose a license"。勾了远端会先产生一个提交，
> 和你本地的历史**互不相关**，push 会被拒绝，还得处理
> `unrelated histories` 错误。保持远端完全空着最省事。

### B. 在 Windows 上

**1. 装 Git for Windows**

去 https://git-scm.com/download/win 下载安装。

安装程序选项很多，但**只有一屏真正要紧**：

| 屏幕 | 选什么 |
|---|---|
| **Adjusting your PATH environment** | **保持默认**："Git from the command line and also from 3rd-party software" |

其余全部默认即可。**两个千万别选**：

- `Use Git from Git Bash only` —— 装了等于没装，`git` 进不了 PATH
- `Use Git and optional Unix tools from the Command Prompt` —— 会把 MSYS 的
  `find` / `sort` / `tar` 塞进 PATH，盖掉 Windows 自带的同名工具

> **换行符那一屏（Line ending conversions）怎么选都不会出事**：
> 本仓库的 `.gitattributes` 强制所有文本文件为 LF，
> 而它的优先级**高于** `core.autocrlf`。

**2. 配置身份**

```sh
git config --global user.name  "你的名字"
git config --global user.email "你的邮箱"
```

**3. 配 SSH 密钥**

```sh
ssh-keygen -t ed25519 -C "win11-fpga-lab"
# 一路回车（密码短语留空）
```

取公钥（cmd）：

```bat
type %USERPROFILE%\.ssh\id_ed25519.pub
```

PowerShell 里换成：

```powershell
Get-Content "$env:USERPROFILE\.ssh\id_ed25519.pub"
```

公钥贴到 Gitee → 设置 → 安全设置 → SSH 公钥，标题 `win11-fpga-lab`。
验证：`ssh -T git@gitee.com`

> ⚠️ **绝对不要一次粘贴多行给 ssh-keygen。** 它是交互式程序，
> 会把你的下一条命令当成"密钥存到哪个文件"的答案。
> 等它跑完、回到提示符，再敲下一条。

**4. 克隆仓库**

```sh
cd ~/Documents
git clone git@gitee.com:milesz26/fpga-lab.git
cd fpga-lab
```

> **HTTPS 的备选方案**：Gitee 开了两步验证（2FA）之后，
> **HTTPS 推送不能用登录密码，必须用「私人令牌」**：
> Gitee → 设置 → 安全设置 → 私人令牌 → 生成（勾 `projects`）。
> 弹凭据窗口时用户名填 `milesz26`、密码填**那串令牌**。
> 否则会直接返回 `403`，报 `Two-factor authentication (2FA) is enabled`。
>
> 这正是**推荐 SSH 的原因**：令牌会过期（几个月到一年），密钥不会。

> **本仓库在 Windows 上的实际情况（2026-10-15）**：
> Git for Windows **已装好**，`git` 已在 PATH 上，**可以直接在 PowerShell
> 或 cmd 里敲**，不必开 Git Bash。仓库是早期用 **GitHub Desktop 的 GUI
> clone** 下来的，现在命令行和 GUI 两条路都能走。
>
> ⚠️ **DSH 的 shell 需要「完全权限」才能用**（`0xC0000142`，根因见
> [环境.md](环境.md)）：会话设成 `workspace-write` 时 pwsh 一律起不来；
> 切成「完全权限」后一切正常。
>
> 另外记住：**DSH 的对话历史不跨机器同步**，两台机器靠的就是本仓库的文件
> （尤其 `docs/进度.md`）。

## 日常循环

### 在 Mac 上（干活 + 推送）

```sh
cd ~/Documents/fpga-lab

git status              # 先看看改了哪些文件
git add -A              # 把改动加入待提交
git commit -m "s01: 完成 NCO 相位累加器 + testbench"

```

### 在 Windows 上（拉取 + 跑 Vivado + 回传）

```sh
cd ~/Documents/fpga-lab

make hooks              # 只在新克隆后跑一次：装上守卫（没 make 见「坑 2」的手工做法）

# ……在 Vivado 里综合 / 实现 / 上板……
# 注意：Vivado 工程建在仓库目录【外面】，别建在 fpga-lab/ 里

git commit -m "s01: NCO 综合通过，附时序报告"
git push
```

### 回到 Mac

```sh
git pull                # 拿到日志，然后让 AI 分析
```

## ⚠️ 两个必须提前排掉的坑

### 坑 1：换行符（已用 `.gitattributes` 解决）

Windows 用 CRLF，Mac 用 LF。不统一会导致：

- shell 脚本在 Mac 上报 `bad interpreter: /bin/sh^M`
- `git diff` 把整个文件标成全改了，看不出真正改了哪里

**已通过仓库根目录的 `.gitattributes` 强制所有文本文件为 LF。**
这个文件的规则优先于 `core.autocrlf` 设置，所以不用担心。

### 坑 2：Vivado 的中间文件

**绝对不能提交**：`*.runs/`、`*.cache/`、`.Xil/`、`*.hw/`、`*.sim/`、
`*.bit`、`*.dcp`、`*.xpr`、`*.wdb`

它们动辄几百 MB 到几 GB，而且每次综合都在变。

**Gitee 的硬限制（社区版 / 个人账号）：**

| 项目 | 上限 |
|---|---|
| **单个文件** | **50 MB** —— 超了直接拒绝推送 |
| **单仓库容量** | **500 MB** |
| 账号总容量（名下所有仓库） | 5 GB |
| 仓库数量 | 1000 个 |

> ⚠️ **换到 Gitee 之后容量反而更紧了。** GitHub 是单文件 100 MB、
> 仓库约 1 GB；Gitee 只有 **50 MB / 500 MB**。原来"50 MB 只是警告"，
> 现在**50 MB 就是硬墙**。
>
> 好在本仓库的 `pre-commit` 守卫卡在 **5 MB**，比它严十倍 ——
> 只要守卫还装着，你就撞不到这堵墙。
>
> 数据来源：[Gitee 产品配额说明](https://help.gitee.com/questions/Gitee%E4%BA%A7%E5%93%81%E9%85%8D%E9%A2%9D%E8%AF%B4%E6%98%8E)

#### ⚠️ 先搞清楚 `.gitignore` 到底能保证什么

这是最容易误解的一点：

> **`.gitignore` 只对"还没被跟踪"的文件有效。**
> 一个文件只要被 `git add` 过一次，它就被 git 跟踪了。
> 从此 **`.gitignore` 对它彻底失效** —— 它会一直出现在
> `git status` 里，一直跟着你提交，直到你 `git rm --cached` 掉它。

所以"我在 .gitignore 里写了"**不等于**"它进不来"。真正危险的是
**第一次**：某次 `git add -A` 把工程目录一并扫进去，那一瞬间就破防了，
之后改 `.gitignore` 也救不回来（已进历史的二进制很难清干净）。

#### 真正的保证：三层，按可靠性从高到低

**第 1 层（最根本）：物理隔离 —— 工程建在仓库目录外面**

```
D:\vivado_prj\s00_blinky\        ← Vivado 工程建在这里
D:\fpga-lab\                     ← git 仓库在这里
```

git 只能看见仓库目录树内部。工程在仓库外面 → **git 在物理上
不可能看到它**。这不是"记得别提交"，是"提交不了"。

这是唯一不需要你记住任何事情的方案，所以它排第一。

**第 2 层：`.gitignore` 兜底**

万一工程还是建到了仓库里（比如手滑），`.gitignore` 能挡住大部分。
本仓库已覆盖 `.runs/` `.cache/` `.Xil/` `.hw/` `.sim/` `.ip_user_files/`
`.gen/` `.srcs/` `.dcp` `.bit` `.bin` `.ltx` `.wdb` `.xpr` `vivado.log` 等。

想自己验证某个文件挡不挡得住，用这条命令（**不要靠猜**）：

```sh
git check-ignore -v --no-index 路径/文件名
```

有输出 = 挡住；没输出 = 挡不住。

**第 3 层：`pre-commit` 守卫（自动拦截，不靠记性）**

前两层都堵不住的情况（已跟踪的旧文件、`git add -f` 强加、
新出现的陌生后缀），靠这个钩子在**提交写库之前**拦下：

```sh
make hooks        # 新克隆仓库后装一次（钩子不进版本库）
make check        # 不提交，只看暂存区有没有问题
```

> **Windows 上如果没有 `make`**（Git for Windows 不自带），
> 在 Git Bash 里直接手工装，效果完全一样：
>
> ```sh
> cp scripts/hooks/pre-commit .git/hooks/pre-commit
> chmod +x .git/hooks/pre-commit
> ```
>
> 同理，自查就直接跑 `sh scripts/hooks/pre-commit`。

它检查三件事：

| 规则 | 触发条件 | 为什么 |
|---|---|---|
| 1 | 路径命中 Vivado 中间产物清单 | 独立于 `.gitignore`，能抓已跟踪的文件 |
| 2 | 单个文件 > 5 MB | Gitee 单文件硬上限 50 MB，早拦早好 |
| 3 | 一次暂存 > 60 个文件 | 文件数突然爆炸 = 多半工程建进仓库了 |

命中就拒绝提交，并打印怎么撤销暂存。

> `.git/hooks/` 目录**不进版本库**，所以每台机器克隆后都要
> 装一次（`make hooks`，或上面的手工 `cp`）。这是它唯一的缺点，但值得。
>
> 确实知道自己在干什么时可以绕过：`git commit --no-verify`。

#### 正确做法（总结）

1. Vivado 工程建在仓库**外面**
2. `make hooks` 装好守卫
3. 只把**文本报告**拷进 `logs/`，再 `git add logs`
4. `git status` 看一眼再提交

给 AI 分析也只需要文本报告。

## 出问题了怎么办

| 现象 | 原因 | 处理 |
|---|---|---|
| `Failed to connect to gitee.com` | **网络连不上**，不是 git 配置问题 | 见下节 |
| `403` + `Two-factor authentication (2FA) is enabled` | HTTPS 里用了登录密码 | Gitee 必须用**私人令牌**，见 B-4 |
| `push` 被拒绝，提示 `rejected` / `non-fast-forward` | 远端有你本地没有的提交 | 先 `git pull`，再 `git push`。**不要用 `-f`** |
| `fatal: refusing to merge unrelated histories` | 建远端仓库时勾了 README | 别勾；或 `git pull --allow-unrelated-histories` |
| 文件里出现 `<<<<<<<` 标记 | 两边改了同一处（合并冲突） | **把文件发给 AI 帮你解**，不要瞎改 |
| `bad interpreter: /bin/sh^M` | 换行符变成 CRLF | 已由 `.gitattributes` 解决 |
| `Permission denied (publickey)` | SSH 密钥没配好 | 重做 A-2 / B-3 |
| `Are you sure you want to continue connecting (yes/no/[fingerprint])?` | 第一次连这台主机 | 输 `yes` 回车（只问一次） |
| 想撤销但还没 commit | —— | `git restore <文件>` |
| 想知道自己改了什么 | —— | `git diff` |

### 连不上远端

**先分清是不是网络问题**：如果之前 push 成功过，远端地址和凭据就是对的，
突然失败基本都是网络。

```sh
git ls-remote origin
```

有输出 = 通了；超时或拒绝 = 不通。

> **换成 Gitee 之后这一节基本用不上了** —— 国内访问 Gitee 不存在
> GitHub 那种连不上的问题。真断了，先重试，再确认不是你这边网络的问题。

> ⚠️ **连不上时不要慌，也不要删东西。** 提交和文件都在本地，
> 网络恢复后 `git pull` → `git push` 就补上了。
>
> **网络恢复后第一件事是 Pull**（远端可能有你缺的提交），否则 push 会以
> `non-fast-forward` 被拒 —— 那是**第二道墙，不是又断网了**，两者别混淆。

#### 附：`github` 备份远端连不上（国内常见，平时用不到）

GitHub 现在只是备份远端，偶尔推一次。上面那套代理 / 端口的办法是**为它准备**的：

1. **挂代理**（如果有）：

   ```sh
   git config --global http.proxy  http://127.0.0.1:7890
   git config --global https.proxy http://127.0.0.1:7890
   ```

   端口换成代理软件实际的。取消：

   ```sh
   git config --global --unset http.proxy
   git config --global --unset https.proxy
   ```

2. **让 SSH 走 443 端口** —— SSH 默认的 22 端口在国内常被封。
   `~/.ssh/config` 里写：

   ```
   Host github.com
     HostName ssh.github.com
     Port 443
     User git
   ```

**记住两条命令就能应付 80% 的情况：**

```sh
git status              # 我现在的状态是什么
git log --oneline       # 历史上发生过什么
```

## 告诉 AI 什么

在这些时候，直接把命令输出贴给 AI（输出很短，不用担心污染上下文）：

- `git status` 的输出 —— 判断当前状态
- 报错信息 —— 判断哪里卡住
- `git diff` 的输出 —— 但**只在改动很小时**；大改动让 AI 自己读文件

**不要**在聊天里粘贴几万行的 Vivado 日志 —— 把文件放进 `logs/` 再 push，
让 AI 用 grep 读。
