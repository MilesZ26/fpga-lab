# Mac ↔ Windows 同步指南

用 **git + GitHub** 在两台机器之间同步，**不要用网盘**。

---

## 总体结构

```
        ┌──────────────────────────┐
        │        GitHub            │  ← 中转站（远程仓库）
        │  github.com/你/fpga-lab  │
        └──────────┬───────────────┘
                   │
        push ↓     ↑ pull        push ↑     ↓ pull
                   │
   ┌───────────────┴──┐     ┌──┴────────────────────┐
   │   Mac（主战场）    │     │  Windows（Vivado 机）  │
   │  写 RTL / 跑仿真   │     │  综合 / 实现 / 上板    │
   │  改 rtl/ tb/ docs/ │     │  只往 logs/ 写东西     │
   └───────────────────┘     └───────────────────────┘
```

**关键分工（这条能让你几乎不会遇到冲突）：**

| 机器 | 只写这些目录 |
|---|---|
| Mac | `rtl/` `tb/` `docs/` `scripts/` `Makefile` |
| Windows | `logs/`（以及必须在 Vivado 里改的 `constr/`） |

两边不碰同一批文件，就不会有合并冲突。

## 一次性设置

### A. 在 Mac 上

**1. 配置 git 身份**（只需一次；会写进每一个提交，永久可见）

```sh
git config --global user.name  "你的名字"
git config --global user.email "你的邮箱"
```

> 建议邮箱和 GitHub 账号用同一个，否则 GitHub 上的贡献统计不会算到你头上。

**2. 配 SSH 密钥**（一次配置，以后免密）

```sh
ssh-keygen -t ed25519 -C "你的邮箱"
# 一路回车即可（密码短语可以留空）

pbcopy < ~/.ssh/id_ed25519.pub     # 把公钥复制到剪贴板
```

然后打开 GitHub → 右上头像 → **Settings** → **SSH and GPG keys** →
**New SSH key** → 粘贴 → 保存。

验证：

```sh
ssh -T git@github.com
# 看到 "Hi 用户名! You've successfully authenticated" 就成功
```

**3. 在 GitHub 上建一个空仓库**

- 仓库名：`fpga-lab`
- 可见性：Private 或 Public 都行（免费账号也支持私有）
- ⚠️ **绝对不要勾选** "Add a README file"、"Add .gitignore"、"Choose a license"

> 为什么：你本地已经有这些文件了。勾了会让远端先产生一个提交，
> 和你本地的历史**互不相关**，push 会被拒绝，还得处理
> `unrelated histories` 错误。保持远端完全空着最省事。

**4. 关联远端并首次推送**

```sh
cd ~/Documents/fpga-lab

git add -A
git commit -m "初始化 fpga-lab 骨架"

git remote add origin git@github.com:你的用户名/fpga-lab.git
git branch -M main
git push -u origin main
```

---

### B. 在 Windows 上

**1. 装 Git for Windows**

去 https://git-scm.com/download/win 下载安装。
安装时**默认选项一路下一步**即可（它会自带一个 Git Bash 终端）。

**2. 配置身份**

在 Git Bash 里：

```sh
git config --global user.name  "你的名字"
git config --global user.email "你的邮箱"

# 保险起见，关掉自动换行符转换（.gitattributes 已经管了，这里是双保险）
git config --global core.autocrlf false
```

**3. 克隆仓库**

```sh
cd ~/Documents
git clone git@github.com:你的用户名/fpga-lab.git
cd fpga-lab
```

Windows 上如果 SSH 没配好，也可以用 **HTTPS + Personal Access Token**：
在 GitHub → Settings → Developer settings → Personal access tokens 生成一个 token
（勾 `repo` 权限），当作密码用。

> 更省事的替代：装 **GitHub Desktop**（图形界面），登录后直接 Clone，
> 之后拉取/推送都点按钮。适合 Windows 那台只做辅助的机器。

## 日常循环

### 在 Mac 上（干活 + 推送）

```sh
cd ~/Documents/fpga-lab

git status              # 先看看改了哪些文件
git add -A              # 把改动加入待提交
git commit -m "s01: 完成 NCO 相位累加器 + testbench"
git push
```

### 在 Windows 上（拉取 + 跑 Vivado + 回传）

```sh
cd ~/Documents/fpga-lab

git pull                # 拿到 Mac 上的最新代码
make hooks              # 只在新克隆后跑一次：装上提交守卫（见「坑 2」）

# ……在 Vivado 里综合 / 实现 / 上板……
# 注意：Vivado 工程建在仓库目录【外面】，别建在 fpga-lab/ 里

# 把 Vivado 的日志和报告拷进 logs/ 对应的子目录
git status              # 先看一眼，别把中间文件带进来
git add -A
make check              # 可选：提交前自查暂存区
git commit -m "s01: NCO 综合通过，附时序报告"
git push
```

### 回到 Mac

```sh
git pull                # 拿到日志，然后让 AI 分析
```

## ⚠️ 两个必须提前排掉的坑

### 坑 1：换行符（已用 `.gitattributes` 解决）

Windows 用 CRLF，Mac 用 LF。不统一会导致：

- shell 脚本在 Mac 上报 `bad interpreter: /bin/sh^M`
- `git diff` 把整个文件标成全改了，看不出真正改了哪里

**已通过仓库根目录的 `.gitattributes` 强制所有文本文件为 LF。**
这个文件的规则优先于 `core.autocrlf` 设置，所以不用担心。

### 坑 2：Vivado 的中间文件

**绝对不能提交**：`*.runs/`、`*.cache/`、`.Xil/`、`*.hw/`、`*.sim/`、
`*.bit`、`*.dcp`、`*.xpr`、`*.wdb`

它们动辄几百 MB 到几 GB，而且每次综合都在变。

**GitHub 的硬限制：**
- 单个文件 > 100 MB → 直接被拒绝
- 单个文件 > 50 MB → 警告
- 仓库建议 < 1 GB

#### ⚠️ 先搞清楚 `.gitignore` 到底能保证什么

这是最容易误解的一点：

> **`.gitignore` 只对"还没被跟踪"的文件有效。**
> 一个文件只要被 `git add` 过一次，它就被 git 跟踪了。
> 从此 **`.gitignore` 对它彻底失效** —— 它会一直出现在
> `git status` 里，一直跟着你提交，直到你 `git rm --cached` 掉它。

所以"我在 .gitignore 里写了"**不等于**"它进不来"。真正危险的是
**第一次**：某次 `git add -A` 把工程目录一并扫进去，那一瞬间就破防了，
之后改 `.gitignore` 也救不回来（已进历史的二进制很难清干净）。

#### 真正的保证：三层，按可靠性从高到低

**第 1 层（最根本）：物理隔离 —— 工程建在仓库目录外面**

```
D:\vivado_prj\s00_blinky\        ← Vivado 工程建在这里
D:\fpga-lab\                     ← git 仓库在这里
```

git 只能看见仓库目录树内部。工程在仓库外面 → **git 在物理上
不可能看到它**。这不是"记得别提交"，是"提交不了"。

这是唯一不需要你记住任何事情的方案，所以它排第一。

**第 2 层：`.gitignore` 兜底**

万一工程还是建到了仓库里（比如手滑），`.gitignore` 能挡住大部分。
本仓库已覆盖 `.runs/` `.cache/` `.Xil/` `.hw/` `.sim/` `.ip_user_files/`
`.gen/` `.srcs/` `.dcp` `.bit` `.bin` `.ltx` `.wdb` `.xpr` `vivado.log` 等。

想自己验证某个文件挡不挡得住，用这条命令（**不要靠猜**）：

```sh
git check-ignore -v --no-index 路径/文件名
```

有输出 = 挡住；没输出 = 挡不住。

**第 3 层：`pre-commit` 守卫（自动拦截，不靠记性）**

前两层都堵不住的情况（已跟踪的旧文件、`git add -f` 强加、
新出现的陌生后缀），靠这个钩子在**提交写库之前**拦下：

```sh
make hooks        # 新克隆仓库后装一次（钩子不进版本库）
make check        # 不提交，只看暂存区有没有问题
```

它检查三件事：

| 规则 | 触发条件 | 为什么 |
|---|---|---|
| 1 | 路径命中 Vivado 中间产物清单 | 独立于 `.gitignore`，能抓已跟踪的文件 |
| 2 | 单个文件 > 5 MB | GitHub 100 MB 硬上限，早拦早好 |
| 3 | 一次暂存 > 60 个文件 | 文件数突然爆炸 = 多半工程建进仓库了 |

命中就拒绝提交，并打印怎么撤销暂存。

> `.git/hooks/` 目录**不进版本库**，所以每台机器克隆后都要
> `make hooks` 一次。这是它唯一的缺点，但值得。
>
> 确实知道自己在干什么时可以绕过：`git commit --no-verify`。

#### 正确做法（总结）

1. Vivado 工程建在仓库**外面**
2. `make hooks` 装好守卫
3. 只把**文本报告**拷进 `logs/`，再 `git add logs`
4. `git status` 看一眼再提交

给 AI 分析也只需要文本报告。

## 出问题了怎么办

| 现象 | 原因 | 处理 |
|---|---|---|
| `push` 被拒绝，提示 `rejected` | 远端有你本地没有的提交 | 先 `git pull`，再 `git push` |
| `fatal: refusing to merge unrelated histories` | 建 GitHub 仓库时勾了 README | 别勾；或 `git pull --allow-unrelated-histories` |
| 文件里出现 `<<<<<<<` 标记 | 两边改了同一处（合并冲突） | **把文件发给 AI 帮你解**，不要瞎改 |
| `bad interpreter: /bin/sh^M` | 换行符变成 CRLF | 已由 `.gitattributes` 解决 |
| `Permission denied (publickey)` | SSH 密钥没配好 | 重做上面 A-2 |
| 想撤销但还没 commit | —— | `git restore <文件>` |
| 想知道自己改了什么 | —— | `git diff` |

**记住两条命令就能应付 80% 的情况：**

```sh
git status              # 我现在的状态是什么
git log --oneline       # 历史上发生过什么
```

## 告诉 AI 什么

在这些时候，直接把命令输出贴给 AI（输出很短，不用担心污染上下文）：

- `git status` 的输出 —— 判断当前状态
- 报错信息 —— 判断哪里卡住
- `git diff` 的输出 —— 但**只在改动很小时**；大改动让 AI 自己读文件

**不要**在聊天里粘贴几万行的 Vivado 日志 —— 把文件放进 `logs/` 再 push，
让 AI 用 grep 读。
